Новый вариант трассировки MBS-fast: пучок обрабатывает группа потоков

Эксперимент от 29 октября 2026. Исходная версия: 86db8babb21651463af2f56aaee2caaf73019862. Изменены только экспериментальные сборки на dima и epyc1.

Результат: обработка небольших пакетов столбиков ускорилась в 1,21–1,54 раза. На реальных пакетах по 256 ориентаций устойчивого дополнительного выигрыша относительно существующего CPU+GPU нет. Новый режим оставлен выключенным по умолчанию. Производственные задачи и очереди не переключались.

Что именно изменилось

На CPU обход дерева пучков уже выполнялся через явный стек. На GPU уже существовали очереди по глубине отражения, и пучки могли сразу передаваться в дифракционное ядро без скачивания на CPU. Поэтому простое «разворачивание рекурсии» не является новым ускорением этой версии.

Новый вариант меняет размер параллельной работы внутри очереди. Раньше один поток GPU брал один пучок и последовательно проверял все грани. Теперь группа из восьми потоков берёт один пучок; потоки параллельно проверяют разные грани. Отражённые пучки попадают в очередь следующего уровня, прошедшие наружу — в массив для дифракции. Группы из 4, 16 и 32 потоков также доступны для исследования; вариант на 32 потока оказался медленнее в первоначальном тесте.

Дополнительно реализовано ограниченное повторное использование выделенной памяти, CUDA stream и событий. Это повторное использование буферов, а не оптического результата. Счётчики и входные данные каждого пакета инициализируются заново. Очереди трассировки по-прежнему освобождаются перед дифракцией. Сохранённые буферы ограничены заданным объёмом; после ошибки не сохраняются, при смене устройства освобождаются. При свободной VRAM менее 512 МиБ буферы после расчёта не удерживаются.

Сохраняются те же ориентации, глубина отражений, коэффициенты Френеля, отсечение и оптические пути. Параллелизм меняет порядок записи пучков и суммирования чисел с плавающей точкой. Фазы между разными ориентациями не смешиваются. Переполнение очереди или неподдерживаемая геометрия вызывают штатный полный расчёт соответствующей работы на CPU.

Измеренная скорость

График показывает отношение времени обработки старого режима ко времени нового. Значение больше единицы означает ускорение. В двух частях графика разные режимы сравнения и размеры пакетов; их результаты нельзя переносить друг на друга.

Отдельный тест только повторного использования буферов дал небольшое улучшение для 446,7 и ухудшение для 631. Оснований включать его повсеместно также нет.

Условия: dima — RTX 3080 Ti, float с reduced phase; epyc1 — V100 16 ГиБ, double. Быстрые неточные математические преобразования отключены. На серверах продолжались другие расчёты. Время отдельных пакетов колебалось; эти измерения не доказывают небольшой выигрыш в несколько процентов. Для повторения сохранены все времена, команды и выходные данные. Сравнение выполнялось на dima/GPU0 и epyc1/GPU1; защищённые крупные задачи не менялись.

Серия с пакетом 32 выполнена на сборке v2, рабочие пакеты и проверки путей — на финальной v3. В v3 уточнено освобождение пустых буферов и запрещено сохранение рабочей памяти после неуспешной трассировки. Версии, исходные команды и файлы обеих серий сохранены в архивах.

Проверка результата

Сравнивались все 16 элементов, их отношения к M11, интегральные характеристики, половинные префиксы ориентаций и парные глубины n и n−2. Проверялись столбик, дроксталл и асимметричная выпуклая форма, когерентный и некогерентный режимы, cutoff off и balanced. В проверках resident все запрошенные ориентации должны пройти GPU: тихий переход на CPU не принимается как успешный тест скорости GPU.

Как воспроизвести

Новые параметры экспериментальные. По умолчанию MBS_GPU_TRACE_CONVEX_SCHEDULE=legacy, MBS_GPU_TRACE_CONVEX_WORKSPACE_MIB=0. Они не выбираются автоматически в fullauto. Режим трассировки включается отдельным обычным флагом resident или hybrid.

env MBS_GPU_TRACE_CONVEX_SCHEDULE=facets8 \
    MBS_GPU_TRACE_CONVEX_WORKSPACE_MIB=64 \
    "$MBS_BINARY" --allow-experimental-environment \
    --po-trace-backend resident \
    --method po --backend cuda --particle 1 398.1 138.9 \
    --symmetry 2 6 --wavelength-um .532 --ri 1.3116 0 \
    --sobol-seed 4096 23 --haar-alpha --threads 2 \
    --orientation-pipeline --orientation-chunk 32 \
    --theta-grid-file theta.txt --phi-points 16 \
    --max-reflections 8 --cutoff-profile off --incoherent \
    --profile-phases --close --output wavefront_trial

theta.txt для этого примера: две строки 160 и 160.01. MBS_BINARY — путь к одной из экспериментальных сборок из таблицы ниже. Размер пакета 32 задаётся для повторения теста; уменьшать рабочие пакеты до 32 ради нового ядра не рекомендуется — прежнее ядро с пакетом 256 само может быть быстрее.

Следующий содержательный шаг

На коротких очередях параллельная проверка граней помогает. На больших очередях уже хватает независимых пучков; дополнительная работа групп увеличивает расход регистров и стоимость управления. Из измерений следует: перед дальнейшим внедрением нужно разнести тяжёлое пересечение полигонов и оптическое расщепление по компактным заданиям, уменьшить локальные копии Beam и проверить объём обмена между этапами. Это предложение следующего эксперимента, а не уже полученное ускорение. Простои всех производственных GPU этой правкой не объявляются устранёнными.

Общая архитектура очередей по этапам описана в PBRT: Mapping Path Tracing to the GPU. Здесь трассируются полигональные пучки с фазой, поэтому результаты графических трассировщиков не перенесены на MBS-fast как обещание скорости.
