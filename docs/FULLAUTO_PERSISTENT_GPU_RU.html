Fullauto: как уменьшены простои четырёх GPU

14 октября 2026. Экспериментальная ветка experiment/gpu-convex-resident-queue-20261014. Короткая методичка.

На рабочих сетках двух призм одинаковый пакет ускорился в 1,41 раза: 10,36 → 7,34 с. Средняя загрузка четырёх карт: 29,0 → 71,5%. Отдельная проверка полного диспетчера: 56 заданий, 12,59 → 7,23 с, 1,74 раза. Эти числа относятся к измеренным пакетам; полная адаптивная сходимость до 2% за них не измерялась.

Что изменилось

  1. Постоянный рабочий процесс на каждую GPU. Fullauto создаёт его один раз и передаёт следующие задания через локальный канал. Контекст CUDA сохраняется. Частица, обработчики и матрицы создаются заново для каждого задания, поэтому результаты разных seeds не смешиваются.
  2. Выбор трассировки на рабочей сетке. После стартового подбора и выбора глубины fullauto сравнивает CPU, резидентный GPU и гибрид CPU+GPU на восьми одинаковых seeds. Резидентный путь оставляет пучки в памяти GPU. Гибрид дополнительно подготавливает другие ориентации на CPU. Кэш трассировки при сравнении отключён. Новый вариант принимается, если он быстрее текущего не менее чем на 5% и расхождение всех 16 элементов ниже min(10⁻⁷, EPS/1024) от M11.
  3. Следующее задание отправляется до проверки файлов предыдущего. Свободная карта продолжает работу, пока контроллер загружает матрицы и записывает подтверждение завершённого блока. Общая очередь распределяет задания по освободившимся картам; одновременного завершения всех карт не требует. Динамическая очередь уже была в предыдущей версии; здесь она работает с постоянными процессами.
  4. Трассировка повторно используется при изменении θ и φ. В RAM сохраняются подготовленные пучки CPU; в VRAM — исходные пучки резидентной трассировки. Дифракция на новых углах пересчитывается. В ключ входят физические параметры, геометрия и ориентации; для файловой геометрии CPU учитывает содержимое файла. Кэш ограничен по памяти и вытесняет старые записи. Попадание в него требует повторного задания на том же процессе; распределение по четырём картам не гарантирует попадание.
  5. Парная глубина доступна GPU-трассировке. Пучки трассируются до верхней глубины; нижняя матрица строится по пучкам до нижней глубины. Для каждой глубины отдельно определяются относительные пороги отсечения выходных пучков. Ограничения парного режима, включая запрет ненулевого отсечения внутри дерева трассировки, сохранены.

Число независимых seeds, угловые веса, когерентное суммирование, интервалы ошибки и бюджет интерполяции EPS/4 не изменены. Кэш пучков — вычислительная оптимизация: он не заменяет усреднение и не уменьшает выборку.

Как запускать

Проверенный бинарник на epyc1:

/home/kirill_epyc/mbs-fast/experiments/fullauto-persistent-20261014/mbs_po_gpu_double

Минимальный пример нового расчёта призмы на четырёх картах; H и D — высота и диаметр призмы в мкм:

/home/kirill_epyc/mbs-fast/experiments/fullauto-persistent-20261014/mbs_po_gpu_double \
  --method po --backend cuda --particle 1 446.7 147.1 \
  --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --fullauto-theta-range 170 180 \
  --fullauto-gpus 0,1,2,3 --output /path/to/new-result --close

Постоянные процессы и выбор трассировки включены по умолчанию. Для воспроизведения фиксированного гибридного режима к этой команде добавляются:

--fullauto-workers persistent --fullauto-trace-backend hybrid \
--threads 16 --orientation-chunk 1024 --trace-cache-mib 256

Это ручная фиксация настроек для данного сервера; она исключает их автоподбор. Для двух независимых расчётов используются непересекающиеся списки --fullauto-gpus 0,1 и --fullauto-gpus 2,3, разные каталоги вывода и общий разумный бюджет CPU-потоков.

ФлагДействие
--fullauto-workers autoПостоянные процессы для CUDA; отдельные процессы для CPU. persistent принудительно сохраняет процессы; process возвращает запуск отдельного процесса на каждый блок.
--fullauto-trace-backend autoПроверить три пути на рабочей сетке. Поиск пропускается для малой начальной выборки N<1024, FP32 и режимов, где резидентная трассировка неприменима. Явные cpu, resident или hybrid фиксируют выбор.
--po-trace-backend cpu|resident|hybridВыбор для отдельного нативного запуска. Fullauto передаёт этот флаг работникам. Конфликт двух явно заданных backend отклоняется. hybrid включает конвейер автоматически.
--trace-cache-mib 256До 256 MiB отдельно для кэша CPU и для кэша GPU, на каждый рабочий процесс. Предел дополнительно уменьшается по доступной RAM и бюджету процесса. Это не предел всей памяти GPU: отдельно нужны рабочие буферы трассировки и дифракции. 0 отключает оба кэша. Для постоянных процессов значение по умолчанию — максимум 256, для одиночного запуска — 0.

Где ускорение применимо

Постоянные процессы и CPU-кэш проверены для обычного PO, поглощения, некогерентного режима, невыпуклой геометрии и аналитических контролей. GPU-трассировка применяется к когерентному FP64 PO без поглощения для выпуклых частиц, которые укладываются в ограничения текущего трассировщика: до 16 граней, до 24 вершин пучка, n≤18. Неподдерживаемые режимы сохраняют CPU-подготовку. При переполнении GPU-блока весь блок пересчитывается прежним путём; частичные матрицы не принимаются.

Для произвольной формы выигрыш определяется её геометрией. Параметры симметрии эта оптимизация не меняет. Автопоиск не навязывает гибрид: в проверенном маленьком fullauto CPU занял 0,300 с, resident — 0,380 с, hybrid — 0,344 с; выбран CPU. На этом тесте ограничение двумя раундами оставило статус requires_further_sampling; достижение 2% не заявляется.

Проверки точности и восстановления

  • На рабочих сетках проверены все 16 элементов при всех θ и их отношения к M11: max |ΔMij|/M11 = 2,865·10⁻⁹; max |Δ(Mij/M11)| = 2,042·10⁻⁹. Интегральные характеристики сверены с масштабом Csca: максимум 1,192·10⁻¹¹.
  • Повторные запросы, смена θ/φ, seed, геометрии, поглощения и когерентности сверены с отдельными процессами. Парные глубины 8/4 проверены на призме и асимметричном тетраэдре, с отсечением выходных пучков и без него. Максимум для тетраэдра ниже 4,14·10⁻¹⁰ от M11. Аналитические контроли при попадании в CPU-кэш также проверены.
  • Кэш действительно использовался: на повторных CPU-сетках 64 попадания из 64; для GPU зафиксированы попадания в кэш сырых пучков. Изменение seed и формы не использовало старый результат.
  • На полном диспетчере max |ΔMij|/M11 = 2,225·10⁻¹⁶. Повторный запуск прочитал все блоки с диска без новых работников.
  • После SIGKILL контроллера на CPU-проверке рабочие процессы завершились, восемь подтверждённых блоков сохранились побайтно. Восстановление дало ту же матрицу, что полный расчёт с начала.
  • Прошли CLI-тесты, регрессия диспетчера и тест устойчивости геометрической топологии. Новые воспроизводимые тесты: tests/test_persistent_workers.py и tests/test_fullauto_persistent_queue.py.

Эти проверки устанавливают эквивалентность вычислительных путей на проверенных случаях. Они не являются новым сравнением PO с ADDA.

Логи, файлы и продолжение после обрыва

В fullauto_history.jsonl записываются GPU, PID, порядковый номер запроса процесса, seed, offset, N, n, парная глубина, θ, φ, блок CUDA, потоки, время внутри и вне вычисления. Выбор трассировки с временами и численными отклонениями хранится в trace_backend_calibration.json. Итоговая команда работников сохраняется в execution_tuning.tsv и снимках параметров.

Каждый каталог jobs содержит command.args, stdout.log, DAT и complete.txt после проверки. В stdout.log есть Persistent worker, Prepared trace reuse и GPU raw trace reuse. RAM/VRAM-кэш исчезает при завершении процесса; дисковые подтверждённые блоки остаются и достаточны для восстановления.

Для продолжения повторите исходную команду с тем же бинарником, аргументами и каталогом вывода либо используйте существующий scripts/replay_fullauto.py для этого каталога. Незавершённый блок будет пересчитан. Проверка хеша бинарника сохранена: предыдущая кампания продолжается своим замороженным бинарником. Испытания кратковременно останавливали выдачу новых заданий, затем исходные контроллеры 1878 и 1880 были продолжены.

Обновление 20 октября: выдача работы перед записью результатов

В новых запусках постоянный диспетчер сначала принимает ответы всех уже закончивших работников и выдаёт им следующие задания. Затем он подтверждает один результат на диске и выполняет подготовку очередного пакета. Перед подтверждением следующего результата он снова проверяет готовых работников. Раньше запись файлов и подготовка после первого ответа могли задерживать выдачу работы остальным свободным картам.

Одновременно на каждом работнике по-прежнему выполняется одно нативное задание. В очереди подтверждения хранится максимум 2 × число работников − 1 завершённых заданий: при четырёх работниках — семь. Это ссылки на сохранённые выходные файлы; все матрицы заранее в RAM не загружаются. Подтверждение complete.txt появляется после прежних проверок. Seed, смещение ориентаций, число ориентаций, θ, φ и порядок суммирования внутри каждого задания сохраняются. Однократный повтор после нехватки памяти сохранён.

Изменение действует автоматически при постоянных работниках и полезно контроллеру, который обслуживает несколько работников. Для расчёта с одним работником этот порядок выдачи остаётся прежним. Уже запущенные процессы не меняются.

Эти величины помогают отличить ожидание контроллера от времени оптического расчёта.
