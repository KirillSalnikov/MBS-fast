# Moving a CUDA checkpoint between cards

For an existing result, keep its original command, output path and `--fullauto-gpus` list. Add `--fullauto-resume-compatible OLD_BINARY --fullauto-dispatch-gpus 0` to run its saved work on visible GPU 0 only. The compatible binary must be the supported original executable that created the checkpoint. The CUDA precision, compiler and backend profile must match.

`--fullauto-dispatch-gpus` accepts 1–8 worker slots. A repeated visible index shares a GPU and requires an explicit per-worker `--fullauto-dispatch-threads` budget. It changes worker placement and concurrency only. It leaves the saved estimator, execution recipe, sampling, optical settings and cache identities unchanged. `fullauto_parameters.json` records the original `selected_gpus` and the actual `dispatch_gpus` and `active_worker_slots`; `worker_start` events record the actual card. Both process and persistent workers obey the override.

Use ordinary `--fullauto-gpus 0` for a new single-card calculation. Dispatch override requires compatible resume. Stop the former controller before starting its replacement. Never run two controllers on the same output directory. Changing cards does not accelerate each task by itself; independent tasks can overlap CPU preparation and GPU processing, and throughput must be measured.

## Equal CPU pools for independent cards

`--fullauto-dispatch-threads 16` fixes the CPU beam preparation and analytic-mean pools to 16 threads in CUDA PO fullauto. This is a placement override: saved sampling, native identities and the original accumulation thread setting stay intact. It applies to new work after cache lookup, so completed blocks remain reusable. On a fresh calculation it conflicts with explicit `--threads`, `--po-prepare-threads` and `--analytic-mean-threads`; choose one policy. On a verified compatible resume, it can explicitly replace the old preparation and mean pools while retaining the original command and checkpoint identity. Automatic preparation profiling cannot replace this explicit choice. The selected saved mean count remains in `analytic_mean_threads`; `effective_analytic_mean_threads` and `dispatch_threads` record the actual override. Native `command.args` and `worker_start` record actual preparation/mean counts. Existing results need `--fullauto-resume-compatible OLD_BINARY` and an accepted compatibility receipt for the exact binaries.

A thread count does not reserve cores. For four queues on a 64-core EPYC, assign disjoint 16-core CPU affinity masks in each systemd service, for example `CPUAffinity=0-15`, `16-31`, `32-47`, `48-63`. Check the physical-core/SMT topology first; these masks assume SMT siblings are 64-127. Services and future children inherit the mask. Avoid setting OpenMP binding on the controller: binding its main thread to one core before fork can restrict a child to that core. Resource sharing with unrelated services is still possible. Measure the resulting GPU waits and wall times; 16 threads is an explicit allocation, not a guarantee of optimal speed.

For three simultaneous queues on a 12-core host, start by budgeting four physical cores per queue. Do not give each queue the entire host. An explicit saved `--threads 2` disables automatic enlargement; changing only the service's affinity will not enlarge that preparation pool. Conversely, requesting eight preparation threads while retaining an affinity mask covering two cores will not provide eight cores. Check both the native command and `/proc/PID/status` (`Cpus_allowed_list`). Compare aggregate completed orientations per second and numerical differences, not GPU utilization alone.

The 2026-11-04 benchmark used a copied production block for a 125.9 µm column, two theta rows and 64 phi points. Keeping `--threads 2` and changing only preparation from two to four threads reduced processing time from 1.101 to 0.607 seconds for 4096 orientations, and from 0.190 to 0.096 seconds for 512. The maximum difference over all 16 elements was 2.85e-8 times M11. These are isolated block measurements under the observed background load, not a measured whole-campaign speedup.
