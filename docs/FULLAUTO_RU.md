# Fullauto: запуск, математика и проверка результата

Руководство к объединённому коду для подготовки MBS-fast 2.0. Режим хранения обновлён 9 ноября 2026.
Источники поведения: `src/FullAuto*.inc`, `src/FullAuto.cpp`, `src/CliOptions.cpp`.
Проценты в примерах относятся к численной погрешности внутри модели PO или GO.

## Самый короткий запуск

```bash
make -C cpu -j2
cpu/bin/mbs_po_mpi --method po --backend cpu \
  --particle 1 5 2 --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --output results/column_5um
```

`po` — физическая оптика; `cpu` — вычисление на процессоре. `--particle 1 L D`
задаёт правильный шестигранный столбик: L — длина вдоль его оси, D — диаметр
основания. Здесь L=5 и D=2 мкм. `--ri REAL IMAG` задаёт комплексный показатель
преломления. Длина волны и координаты частицы должны иметь одинаковые единицы.
`0.02` — допуск 2%. Каталог `--output` хранит опубликованные матрицы и параметры.
Новый расчёт по умолчанию хранит рабочие блоки в памяти. Для восстановления
после остановки добавьте `--checkpoint`: он включает периодические снимки
рабочего состояния. Без этого флага опубликованная матрица пригодна для просмотра,
но не заменяет полный снимок для продолжения адаптации.

Не нужно добавлять Sobol, число φ, стартовые ориентации, коэффициенты аналитической
модели и отсечение только ради включения автоматики: контроллер задаёт их сам.
Это один процесс контроллера; не запускайте несколько MPI-контроллеров в одну папку.

Частица из файла с максимальным габаритом Dmax=5 мкм:

```bash
cpu/bin/mbs_po_mpi --method po --backend cpu \
  --particle-file examples/cube.particle --resize-dmax-um 5 \
  --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --output results/file_5um
```

Dmax — максимальное расстояние между вершинами. Оно отличается от длины столбика,
его диаметра основания и диаметра равновеликого шара. Данные о симметрии в файле
не считаются доказательством: сначала используется полная область ориентаций.

## GPU, конусы и подробная команда

Сборка FP64 для V100: `make -C gpu fp64 GPU_ARCH=70 -j2`.
Для RTX 3080 Ti используйте архитектуру 86, для RTX 4090 — 89.
Сборка `fp32` быстрее на потребительских картах, но её арифметическую погрешность
нужно проверить отдельно: статистический интервал Sobol её не измеряет.

```bash
# Вперёд: 0–25 градусов, один GPU.
CUDA_VISIBLE_DEVICES=0 gpu/bin/mbs_po_gpu_double \
  --method po --backend cuda --particle 1 100 50 \
  --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --fullauto-theta-range 0 25 \
  --output results/column_100_forward

# Назад: 170–180 градусов, два GPU одного контроллера.
CUDA_VISIBLE_DEVICES=0,1 gpu/bin/mbs_po_gpu_double \
  --method po --backend cuda --particle 1 100 50 \
  --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --fullauto-theta-range 170 180 \
  --fullauto-gpus 0,1 --output results/column_100_backward
```

Номера GPU отсчитываются после применения `CUDA_VISIBLE_DEVICES`.
Для двух независимых размеров запускайте два контроллера с разными каталогами
и непересекающимися списками GPU. Флаги старого multisize не совмещаются с fullauto.

Расширенный пример намеренно фиксирует часть параметров:

```bash
CUDA_VISIBLE_DEVICES=0 gpu/bin/mbs_po_gpu_double \
  --method po --backend cuda --particle-file examples/cube.particle --resize-dmax-um 5 \
  --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --fullauto-theta-range 170 180 \
  --max-reflections 8 --phi-points 4 \
  --fullauto-initial 512 --fullauto-min-correction 256 \
  --max-orientations 1048576 --threads 4 \
  --fullauto-rotation-symmetry off --fullauto-mirror off \
  --cutoff-profile off --fullauto-analytic-controls off \
  --output results/fixed_settings
```

| Флаг | Что меняет |
|---|---|
| `--max-reflections 8` | Фиксирует целевую глубину. Автопоиск 6…18 выключен. Финальная проверка может обнаружить недостаточную глубину. |
| `--phi-points 4` | Фиксирует число наблюдательных азимутов; поиск φ не заменит это значение. |
| `--fullauto-initial 512` | Начальное N на один seed, а не окончательное N. |
| `--fullauto-min-correction 256` | Минимальное число ориентаций поправки на один seed. |
| `--max-orientations 1048576` | Верхняя граница N; достижение границы не означает сходимость. |
| `--threads 4` | Явное число потоков; автоматический подбор не должен его переопределять. |
| `--fullauto-rotation-symmetry off` | Не искать сокращение области по вращениям тела. |
| `--fullauto-mirror off` | Не использовать зеркальное сокращение. |
| `--cutoff-profile off` | Фиксировать расчёт без отсечения; автоматический balanced с поправкой не включается. |
| `--fullauto-analytic-controls off` | Вычислять полную PO без аналитических контрольных компонент. |

Обычно короткая команда удобнее. Расширенный вариант нужен для воспроизводимых
сравнений и проверки одной настройки. Явное ограничение имеет приоритет, но
несовместимые режимы должны завершаться ошибкой, а не молча игнорироваться.

## Что означает требуемая точность

M — матрица Мюллера 4×4; она переводит падающий вектор Стокса в рассеянный.
θ — угол рассеяния: 0° вперёд, 180° назад. Для каждого проверяемого θ контролируются
все 16 элементов. Масштаб абсолютной ошибки Mij — M11 того же угла. Поэтому нуль
M12 не приводит к делению на M12. Дополнительно по умолчанию проверяются отношения
Mij/M11; их погрешность задаётся в абсолютных долях отношения.

Для каждого элемента и угла складываются его статистическая оценка, его оценка
интерполяции и фиксированные резервы. Максимум берётся **после** этого сложения:

$$E=\max_{\theta,j}\{e_{\mathrm{stat},\theta j}
+e_{\mathrm{interp},\theta j}+r_{\mathrm{fixed}}\}.$$

Отдельно проверяются непосредственно вычисленная и полная выходная матрицы.
Нельзя складывать максимальные статистическую и интерполяционную ошибки разных
элементов и выдавать это за реализованный критерий.
Интерполяционный допуск равен EPS/4: для 2% это 0,5%, для 1% — 0,25%.
Резервы зависят от включённых проверок глубины, симметрии, аналитики и исполнения.
Фактические значения записаны в файлах параметров и `pointwise_budget_production.csv`.

95%-интервалы здесь поточечные и статистические. Они не гарантируют одновременно
95% для всех углов, не доказывают отсутствие узкого пика между проверками и не
измеряют ошибку самой модели PO относительно точного электромагнитного решения.
Отключённая проверка обозначается как непроверенная, а не как нулевая ошибка.

## Последовательность работы

1. Проверить аргументы, геометрию, единицы и доступные ресурсы. Построить запрошенную
   сетку вывода и стартовую оценку N. Если есть совместимый чекпоинт, восстановить его.
2. Подобрать целевую глубину внутренних взаимодействий, если она не задана.
   На CUDA перед этим проводится короткая настройка исполнения и φ для пилота;
   полный подбор выполняется после выбора глубины.
3. Проверить допустимые симметрии. Обучить аналитические контрольные коэффициенты
   и проверить их на других seed. Выбрать φ и параметры исполнения по стоимости
   достижения допуска, а не только по времени одного малого запуска.
4. Вычислять опорные и проверочные θ, восемь независимых реплик и уровни поправок.
   Сохранять завершённые блоки; использовать прежние блоки для совпадающих запросов.
5. Оценить статистику, остаток интерполяции и устойчивость префиксов. Уточнять
   ориентации или θ там, где это требуется. Шумный остаток сначала получает больше
   парных образцов; новый опорный θ добавляется при подтверждённой структуре.
6. Опубликовать промежуточную матрицу и оценки. После прохождения рабочих критериев
   выполнить включённые независимые и физические проверки и сохранить итог.

`--fullauto-final-checks off` отключает финальные перепроверки. Это меняет объём
проверенного результата, а не делает пропущенные проверки успешными. По умолчанию
их сохраняют. Такой режим нельзя использовать с GO balanced, которому обязательна
проверка ошибки отсечения. При явном `--convergence-passes` число проходов сохраняется.

## Стартовое N и глубина n

N — число ориентаций **на одну** Sobol-реплику и уровень. Восемь реплик с N=512
означают 4096 ориентаций базового уровня; поправки имеют свои N.
n — максимальная глубина внутренних взаимодействий в трассировке.

По умолчанию coherent PO использует эмпирическую оценку по уже завершённым
расчётам, размеру, длине волны, диапазону θ, форме и допуску. Это только начало,
а не предсказанная гарантия сходимости. В реализации:

$$\begin{aligned}
s={}&8.5128934+2.0264267\log_2(1+L_{\max}/(8\lambda))\\
&+0.6416260\,I(\theta_{\max}>90^\circ)
+4.0403518\,I(\Delta\theta>90^\circ)\\
&+0.8222766\,I(\text{controls off})
-2.7035215\,I(\text{не столбик типа 1}).
\end{aligned}$$

$$N_{\mathrm{forecast}}=2^s(0.01/\mathrm{EPS})^2,\qquad
N_0=\operatorname{pow2up}\!\left(\max(512,N_{\mathrm{forecast}}/16)\right).$$

Lmax — наибольшее ребро в оценке геометрии; I — индикатор условия (0 или 1);
pow2up — округление вверх до степени двойки. До округления применяется предел,
связанный с `--max-orientations`. Коэффициенты модели получены по 234 записям,
73 уникальным когерентным конфигурациям; перенос на новую форму проверяется
последующей сходимостью. Формула со знаком «не столбик» отражает эти данные,
а не общий физический закон для произвольных частиц.

После углового пилота эта оценка становится верхним предложением для первого
производственного раунда. По измеренному времени контроллер выбирает степень
двойки с ориентиром 1800 секунд работы на одну GPU; при отсутствии измерений
начинает с 512 на seed. Уже готовые полные префиксы восьми seed и минимальные
бюджеты поправок сохраняются. `initial_production_work.json` содержит
предложенное и выбранное число ориентаций, прогноз времени и признак наличия
измерений. Это ориентир стоимости, а не гарантия завершения за 30 минут.
Решение принимается без чтения значений производственной матрицы.
Явный `--fullauto-initial`, загруженная адаптивная конфигурация и
`--fullauto-local off` сохраняют заданный старт. Следующие раунды уточняются
по ошибке; все критерии приёмки остаются прежними. Ранняя первая оценка
не означает, что расчёт сошёлся.

`--fullauto-initial-model xi` возвращает старый ориентир beta×gamma по мелкому
дифракционному шагу; он часто завышает старт. Явный `--fullauto-initial` заменяет
обе модели. Для GO остаётся ограниченный старт по оптической толщине поглощения;
GO без поглощения масштабно инвариантна. Некогерентная PO сохраняет дифракцию
отдельных пучков и получает собственное предложение до округления вверх до степени 2:

$$N_{\mathrm{proposal}}=\min\{8192,\max[512,\pi D_{\max}/\lambda,
512(1+\sqrt{4\pi|\operatorname{Im}m|D_{\max}/\lambda})]\}.$$

Здесь Dmax — максимальный габарит, λ — длина волны, Im m — мнимая часть
показателя преломления. Это ограниченная оценка стартовой работы, а не
прогноз достигнутой точности. Ограничитель времени первого раунда может её
уменьшить. Явный `--fullauto-initial` по-прежнему имеет приоритет.

Новый поиск n использует критерий `common-reference-local-pilot-v2`.
По умолчанию целевая глубина остаётся в пределах 6…18. Сначала проверяются
кандидаты 6 → 12 → 18, до первого прошедшего кандидата. Затем проверяются все
пропущенные меньшие глубины с шагом 2. Например, после успешного n=12 проверяются
8 и 10, а после успешного n=18 — 8, 10, 14 и 16. Поиск не предполагает, что
остаток монотонно убывает с n: для когерентных матриц это может быть неверно.
Параметры границ и старта: `--fullauto-depth-start`, `--fullauto-depth-max`,
`--fullauto-depth-pilot`, `--fullauto-depth-order`.

Кандидат сравнивается непосредственно с общей более глубокой матрицей, а не
только с соседней глубиной n+2. При стандартном максимуме 18 рассчитываются
три матрицы: кандидат M(n), промежуточная опора M(20) и глубокая опора M(22).
В каждой тройке совпадают число ориентаций, восемь Sobol-наборов, φ, углы θ и
параметры отсечения. Разности считаются попарно, с учётом общей случайной части.
Проверяются все 16 элементов относительно M11 глубокой опоры и нормированные
отношения элементов к M11.

Пусть B=EPS/4 — бюджет выбора глубины. Для принятия требуются одновременно:

- верхняя 95%-ная оценка разности M(n) и M(22) не больше B;
- верхняя оценка разности M(20) и M(22) не больше B/4.

При `--fullauto .04` это соответственно **1%** и **0,25%**. Второе сравнение
проверяет устойчивость самой опоры. Это две проверки конечных глубин, а не
доказательство отсутствия вклада всех отражений после n=22. Общей гарантии
доверия одновременно для всех углов этот пилот также не даёт. Если максимум
изменён, используются глубины `min(max+2,28)` и `min(max+4,30)`: при максимуме
28 проверка опоры становится 28/30, чтобы не выйти за предел трассировщика 30.

Старт пилота по умолчанию `min(512,N0)` на один независимый набор. Это отдельная
выборка, не большое стартовое N основного усреднения. Если опора прошла свою
проверку, исход для кандидата определяется так:

- верхняя граница ниже бюджета — кандидат прошёл на данном угле;
- нижняя граница выше бюджета — глубины недостаточно;
- интервал пересекает бюджет — статистики пока недостаточно.

При неопределённом результате N удваивается: обычно 512 → 1024 → 2048 → 4096.
В PO расширяются только ещё спорные углы; прошедшие строки сохраняют свои
матрицы и N. Для технически необходимого пакета из двух углов программа может
добавить соседнюю строку, но не подменяет ею уже принятую оценку. В GO пилот
повторяет полную сетку угловых ячеек. Неустойчивый знаменатель M11, нечисловая
оценка или нехватка выборки остаются неопределённостью, а не доказанной
нехваткой глубины.

Первый проход ограничен `min(max-orientations,max(Nпилот,4096))`. Если при этом
никто не прошёл и опора не получила подтверждённого отказа, неопределённые
кандидаты могут продолжить удвоение до
`min(max-orientations,max(4096,256×Nпилот))`. Для стандартного Nпилот=512 это
131072 на набор. Явный `--max-orientations` всегда ограничивает оба прохода.
Достижение лимита не считается успехом: неразрешённый поиск останавливается с
`depth_selection_unresolved`. При восстановлении используются готовые
префиксы ориентаций; проверка не требует заново считать уже сохранённые блоки.
Для обычного запуска с включённым накоплением размер блока на время пилота
уменьшается до `min(исходный блок,max(512,Nпилот))`: переход 512 → 1024 добавляет
следующие 512 ориентаций. После подбора восстанавливается производственный
размер блока. Явный `--fullauto-orientation-block` и загруженная адаптивная
конфигурация сохраняют приоритет; отключённое накопление не обещает этого
переиспользования.
Нижняя граница блока 512 предотвращает сотни коротких запусков при явно
заданном очень маленьком пилоте, например N=8. Само число ориентаций пилота
остаётся заданным пользователем; маленькие ранние удвоения могут повторять
этот короткий префикс до перехода к блокам накопления.

Из проверенных и прошедших кандидатов выбирается вариант с наименьшим прогнозом
затрат. Прогноз использует измеренное время расчёта кандидата, дисперсию пилота
и фактические N по углам. Это ориентир стоимости при текущем φ: последующий
подбор φ, аналитических поправок и распределения работы между уровнями глубины
может изменить время. Поэтому выбранное n не объявляется ни доказанным
минимумом, ни гарантированно самым быстрым для полного расчёта. Сам прогноз
никогда не разрешает принять кандидата, который не прошёл проверку ошибки.

`depth_selection_policy.json` сохраняет критерий, опорные глубины и лимиты.
`depth_search_progress.json` показывает текущую проверку. В
`fullauto_history.jsonl` события `depth_candidate` и `depth_pilot_decision`
содержат оценки и причины действий; `depth_candidate_cost` — прогноз стоимости.
Снимки в `depth_pilot_snapshots/` содержат матрицы и `parameters_accuracy.csv`
с N, границами ошибок и решением для каждого θ. Итог находится в
`depth_selection.json`; `automatic_depth_policy.tsv` связывает его с
конфигурацией и версией критерия.
`depth_candidates.csv` сводит решения по всем проверенным глубинам, их ошибки,
прогноз стоимости и выбранную строку. В `depth_selection.json` поле
`row_parameters` указывает на таблицу N и ошибок именно выбранного кандидата.

При продолжении старого расчёта с уже созданным производственным чекпоинтом
сохраняется прежнее выбранное n. Оно отмечается в
`depth_selection_resume_policy.json` как `legacy-neighbor-pilot-retained`,
`common_reference_verified:false`. Обновление бинарника само по себе не означает
перепроверку старых матриц новым критерием. Для нового критерия повреждённая или
отсутствующая запись подтверждения не разрешает молча изменить глубину уже
начатого производственного усреднения.
Если включённый финальный контроль потребовал повысить n, переход сначала
сохраняется в `depth_promotion_pending.tsv`, затем прежние служебные файлы
переносятся в `depth_attempts/n...`. После прерывания переход завершается
по проверенным контрольным суммам; `depth_promotion_floor.tsv` не позволяет
вернуться к уже отвергнутой глубине даже при потере файла пояснения.
Конфликт исходных и архивных файлов останавливает восстановление, сохраняя
обе копии и рассчитанные блоки.

`--max-reflections N` имеет приоритет и отключает автоматический поиск n.
`--fullauto-final-checks off` отключает итоговые повторные проверки, но сохраняет
описанный стартовый подбор для нового автоматического расчёта. При включённых
итоговых проверках остаётся отдельное сравнение выбранной глубины n с n+2.

## Усреднение Sobol и три угла Эйлера

Поворот задаётся R=Rz(α)Ry(β)Rz(γ). Для равномерного случайного положения частицы
нужна мера Хаара — равномерная мера на группе трёхмерных поворотов SO(3):

$$\langle M\rangle=\frac{1}{8\pi^2}
\int_0^{2\pi}\!d\alpha\int_0^\pi\!\sin\beta\,d\beta
\int_0^{2\pi}\!M(R,\theta)\,d\gamma.$$

Для полной области точки u,v,w из единичного куба превращаются в
cosβ=1−2u, γ=2πv, α=2πw. Равномерно раскладывать β без веса sinβ было бы неверно.
Sobol строит последовательность с равномерным покрытием куба; вложенное
перемешивание Owen с seed делает независимые рандомизированные реплики.
Это не независимые случайные точки внутри каждой реплики и не декартова
сетка Nα×Nβ×Nγ. Поэтому сравнение одного N Sobol с произведением трёх сеточных
размеров не означает такое же увеличение точности или ускорение.

Восемь seed используются для оценки неопределённости. Пусть Yr — целая оценка
матрицы из реплики r, включая связанные поправки. Тогда

$$\bar Y=\frac18\sum_{r=1}^8Y_r,\quad
s_Y^2=\frac17\sum_{r=1}^8(Y_r-\bar Y)^2,\quad
h_{95}=t_{0.975,7}\,s_Y/\sqrt8.$$

t — квантиль распределения Стьюдента, около 2,365. Для Mij/M11 учитывается
ковариация числителя и знаменателя и проверка разрешимости отношения; малый
шумный знаменатель не разрешается заменой на удобный нулевой интервал.
Данные половинных префиксов дополнительно проверяют устойчивость.

N растёт степенями двойки. Уже рассчитанный префикс используется повторно;
`--sobol-offset` в рабочих заданиях задаёт его продолжение. Производственные,
обучающие и проверочные seed разделены. Один seed не заменяет восемь реплик.

Sobol — наиболее практичный текущий вариант для наших неоднородных PO-интегралов
и локального уточнения: можно наращивать префикс и совместно считать разности
уровней. Это не доказательство превосходства над Лебедевым или разложением Вигнера
на любой форме. Их преимущества зависят от гладкости и симметрии конкретной задачи.

## Зачем φ, если уже есть α

α вращает частицу вокруг направления падающего света. φ задаёт азимут наблюдателя.
При полном усреднении по α дополнительные φ могут снижать дисперсию, сохраняя
математическое ожидание. В каждой ориентации это разные операции; для поляризационных
элементов также нужен корректный поворот базиса Стокса.

`--haar-alpha` добавляет третью координату Sobol. Fullauto PO использует её сам.
По мере увеличения числа ориентаций не требуется автоматически делать φ столь же
мелким, как в старой двухугловой сетке. Но φ=1 не гарантирует минимальное время:
дополнительные направления наблюдения используют уже трассированные пучки.
Контроллер выбирает компромисс «стоимость × дисперсия» и может уточнять φ локально.
`--phi-points N` закрепляет правило. `--sobol-seed 32768 SEED` относится к ручному
запуску; в fullauto используйте `--fullauto-initial 32768` для начального N.

В следующем проверяемом кандидате оценка стоимости φ для некогерентной PO
учитывает также шум соседних углов и трёхточечных контрастов. Он оценивается
по уже рассчитанным восьми реализациям пилота с теми же допусками v4, что и
в основном расчёте. Дополнительных оптических заданий для этого ранжирования
не требуется. Это помогает не выбирать дешёвое φ, которому затем нужна большая
выборка для углового критерия. Правила принятия точности, бюджеты ошибок и явно
заданное φ не меняются. Ускорение полного расчёта этим изменением ещё проверяется.

Вращательная и зеркальная симметрии относятся к телу и проверяются отдельно.
Шестикратная симметрия столбика не даёт права делить лабораторное α или φ на шесть.
Для произвольной частицы без подтверждённой симметрии остаётся полная область.

Отказ аналитической контрольной модели не отменяет зеркальную симметрию формы.
После такого отказа fullauto заново проверяет `mirror-gamma` на обычной PO,
при выбранных φ и глубине отражений. Если парная проверка всех 16 элементов
проходит прежний допуск `epsilon/256`, зеркальное ускорение сохраняется.
При неуспехе автоматический режим использует полный диапазон γ.
Явное `--fullauto-mirror off` сохраняется; явное `--mirror-gamma` при провале
проверки приводит к ошибке, а не к скрытой смене режима. Решение записывается
в `analytic_fallback_mirror.json`, численная проверка — в
`mirror_verification.json`. Проверка привязана к углам, φ, глубине, бинарнику,
режиму и коэффициентам аналитического контроля. Контрольная точка сохраняет
выбранный режим: обновление программы само по себе не переключает уже
сохранённый расчёт с полного γ на зеркальное восстановление.

## Что вычисляется аналитически

### Дифракция отдельного пучка

Плоский многоугольный выходной пучок даёт интеграл вида

$$F(\mathbf q)=\int_A\exp(i\mathbf q\cdot\mathbf x)\,dA.$$

Для постоянной амплитуды на плоской апертуре его можно свести к сумме по рёбрам.
При малой фазе и почти нулевых знаменателях используются устойчивые пределы и
моменты. Это аналитическое вычисление дифракции **для данной ориентации**;
оно не выполняет всего ориентационного усреднения. Комплексные амплитуды пучков
складываются когерентно до перехода к матрице Мюллера. В некогерентном режиме
складываются отдельные интенсивности: это другая физическая постановка.

### Аналитические контрольные компоненты

Пусть C(R,θ) — дешёвая физическая модель с известным средним μC(θ), а M — полная
PO. Контрольная переменная даёт оценку

$$\widehat M=\overline{M-bC}+b\mu_C.$$

b — коэффициент уменьшения дисперсии, обученный отдельно от производственной
выборки. При корректном μC вычитание и возврат среднего сохраняют ожидание.
Внутренние пути, затенение и интерференция, отсутствующие в C, остаются в M−bC.
Поэтому усреднить коэффициент Френеля и заменить им все отражения недостаточно.

Контроли включают самовклады отражающих граней и модель тени. Для M11 используются
их физические средние; поляризационные контроли и поворотные компоненты проходят
собственную проверку. Неподходящие компоненты отключаются после проверки по полной
PO: это допустимый отказ от ускорения, а не отказ от расчёта рассеяния.

### Моменты Френеля и фазовые средние

μ — косинус угла падения на грань, rs(μ), rp(μ) — коэффициенты Френеля двух
поляризаций. Отражательная способность R(μ)=(|rs|²+|rp|²)/2 зависит от μ.
Момент — интеграл этой функции с весом; например,

$$c_\ell=\frac{2\ell+1}{2}\int_0^1 R(\mu)P_\ell(\mu)\,d\mu,$$

где $P_\ell$ — полином Лежандра. В физических ядрах присутствуют также геометрические
и проекционные веса. Теорема сложения и разложение плоской волны позволяют
аналитически усреднить угловые фазовые множители, используя сферические функции
Бесселя. Общие моменты повторно используются для многих θ. Гладкие одномерные
интегралы Френеля, таблицы радиальных ядер и часть интегралов по рёбрам остаются
численными. Это аналитико-численный контроль, не замкнутое решение всех путей.

| Настройка | Смысл |
|---|---|
| `--analytic-facet-average` | Явно запросить аналитический контроль граней; fullauto умеет включать и проверять его автоматически. |
| `--analytic-shadow-control circular` | Контроль тени круглой апертурой с геометрически определённой площадью. Отличие от реальной формы остаётся в остатке. |
| `--analytic-mean-cache FILE` | Файл кэша средних для совпадающих параметров. В fullauto этот параметр можно оставить автоматике. |
| `--analytic-mean-threads N` | Потоки подготовки аналитического среднего; явное значение фиксируется. |
| `--fullauto-analytic-controls off` | Полная численная PO, без этих контролей. |

Для большой частицы подготовка среднего может стоить заметного времени и RAM.
Кэш экономит повторную подготовку; это не дополнительный физический эффект.
Контроль интенсивностей граней доступен и для некогерентной PO: его выборочное
значение вычитается, а среднее той же функции добавляется. Интерференция между
пучками в некогерентную матрицу не добавляется. Отдельный экспериментальный
`--analytic-backscatter` остаётся когерентным. Режим GO не использует PO-контроли.

## Поправки по глубине и отсечению

Несколько уровней используют тождество

$$\mathbb E[M_{n_L}]=\mathbb E[M_{n_0}]
+\sum_{\ell=1}^{L}\mathbb E[M_{n_\ell}-M_{n_{\ell-1}}].$$

Это многоуровневая оценка: дорогие разности могут иметь меньшую дисперсию, чем
полная матрица, и потому требовать меньше ориентаций. Оба слагаемых разности
используют одинаковые ориентации. Где поддерживается, общая трассировка сохраняет
результаты для двух глубин. Разность берётся между матрицами полных когерентных
решений соответствующей глубины, а не между интенсивностями отдельно отброшенных
лучей. Ковариации учитываются через полную сумму внутри каждой из восьми реплик.

Для некогерентной PO каждый уровень складывает матрицы отдельных пучков.
Общая трассировка двух глубин теперь доступна и здесь для выпуклых форм.
До её включения два независимых seed сравнивают обе матрицы с отдельными
трассировками на тех же ориентациях: все 16 элементов и отношения к M11.
Порог численного расхождения — min(10⁻⁷, EPS/1024) для double и
min(10⁻⁶, EPS/4096) для float; EPS — заданный допуск fullauto как доля единицы.
Результат записывается в `depth_sharing_verification.json`. При неудаче или
неподдерживаемой форме остаются отдельные трассировки. Аналитические контрольные
модели интенсивностей граней доступны и для некогерентной PO независимо от общей
трассировки глубин.

По умолчанию PO, включая некогерентную, использует balanced с парной поправкой:

$$\widehat M=\overline{B}_N+\overline{(O-B)}_m.$$

B — расчёт с отсечением, O — без отсечения. Ориентации O и B в поправке совпадают.
Физическая цель остаётся O. Небольшой m экономит работу, пока дисперсия поправки
достаточно мала; в коде используются минимальные блоки и доля префикса.
Отдельный подбор пресетов по умолчанию больше не нужен. Время всё равно зависит
от числа пучков поправки и её дисперсии: гарантированного ускорения нет.

Явный `--cutoff-profile balanced` фиксирует пресет и не эквивалентен автоматической
схеме с O−B. Явные пороги также имеют приоритет. Для GO balanced применяется
отдельная проверка смещения относительно off, описанная в `GO_BALANCED.md`.

При доминировании шумной поправки контроллер может выполнить до двух коротких
подраундов перед дорогим увеличением базовой выборки. Теперь подраунд берёт до
128 проблемных углов, включая разные уровни поправки, и увеличивает выбранные N
в 2–4 раза. Прогноз его затрат должен укладываться в прежние 10% затрат
отложенного расширения базы. Восемь реплик, общие ориентации в разностях и
критерии приёмки сохраняются. Прогноз времени не подтверждает точность.

Начальный N=512 больше не отключает автоматическое сравнение трассировщиков.
При выбранных φ и n сравниваются CPU, resident GPU и hybrid на 512–2048
ориентациях на seed, с учётом `--max-orientations`. Другой трассировщик выбирается
при численном совпадении и измеренной экономии не менее 5%. Неподдерживаемая
геометрия или поглощение сохраняют прежний путь вычисления.

При автоматическом отсечении готовые блоки старых некогерентных расчётов без
отсечения сохраняются, а новые подходящие блоки используют balanced с парной
поправкой off−balanced. Оба варианта оценивают одну матрицу без отсечения;
при объединении учитывается число ориентаций каждого блока. Переход записывается
событием `cutoff_estimator_restore`. Явно заданное отключение отсечения сохраняется.
Аналитические коэффициенты и решение об общей трассировке глубин восстанавливаются
из чекпоинта: старые данные без аналитического контроля автоматически не переделываются.

Ограничитель длительности раунда учитывает худшую ошибку интерполированного
результата и сохраняет совместное уточнение его опор. Раньше он ранжировал только
ошибки прямых расчётов; из-за этого худший интерполированный угол мог ждать много
раундов. Критерий точности сохранён.

## θ, интерполяция и короткие раунды

Выходная сетка, опорные θ и проверочные θ — разные множества. Без внешней сетки
fullauto строит достаточно плотную сетку вывода из размера, λ и диапазона. Прямой
расчёт производится на адаптивном подмножестве. `--theta-grid-file FILE` фиксирует
именно углы вывода, но сам по себе не означает прямое вычисление каждой строки.

В некогерентной физической оптике все 16 исходных элементов интерполируются
кусочно-линейно между соседними опорами:
$M(\theta)=(1-t)M_i+tM_{i+1}$, где
$t=(\theta-\theta_i)/(\theta_{i+1}-\theta_i)$ и $0\leq t\leq1$.
Отношения элементов к M11 вычисляются после этой операции, а не интерполируются
отдельно. Опорные значения сохраняются точно; внутри интервала новые экстремумы
элементов не появляются. При положительном M11 это верно и для отношений.
Шум самих опор интерполяция не устраняет. Когерентная PO сохраняет прежнюю
кубическую интерполяцию, GO — прямой расчёт угловых ячеек.

Оператор I использует одинаковые фиксированные геометрические веса для всех
реализаций, производственного результата и проверок; он линеен по значениям
матрицы и перестановочен с усреднением. Проверяется остаток
$\Delta=M(\theta)-I[M_{\mathrm{support}}](\theta)$ на одинаковых ориентациях. Это
позволяет сокращать общий ориентационный шум. Бюджет остатка теперь отдельный:
он не наследует максимальное N соседнего дорогого угла. При различных рабочих
φ для остатка обе стороны используют единое правило φ. Основной расчёт сохраняет
свои правила. Выборка остатка фиксируется до чтения значений, а затем уточняется
по неуспешной проверке.

Новый опорный угол начинается с обычного стартового бюджета. Полные уже готовые
префиксы восьми seed сохраняются. Планировщик ограничивает объём следующего раунда
по измеренной стоимости; ориентир 1800 рабочих секунд на GPU не является жёстким
сроком. Неделимый префикс, трассировка или чтение кэша могут занимать больше.

В проверяемом кандидате шумные некогерентные пары/тройки с разными N могут
доуточняться вместе с ближайшими опорами — не более восьми узлов в одной группе.
У них одинаковое φ; исходные N находятся в диапазоне от половины до полного
максимума исходной пары/тройки. Планировщик догоняет этот максимум, не создавая
нового и не распространяя его по цепи вдоль конуса. Группа общая для всех уровней
и сохраняется в `angular_cohorts.csv` для восстановления. Ограничитель времени,
допуски и все проверки точности сохраняются. Это изменение проходит отдельное
полное испытание; предыдущий кандидат с одним лишь новым выбором φ проблему
последовательного догоняния не устранил.

После автоматического увеличения φ ограничитель действует и на первый проход
новой выборки, даже если это уже поздний раунд. Без достаточных измерений
изменённые строки начинают с N=512 на базовом уровне и минимального бюджета
поправок; измеренная стоимость позволяет увеличить эти значения. Старые строки,
оставленные на прежнем φ, сохраняют свои бюджеты. Явный `--fullauto-initial`
и старт из конфигурационного файла эта защита не заменяет.

Для balanced с поправкой стоимость включает все слагаемые
$B_N+O_m-B_m$, где $m=\max(64,N/8)$: $B$ — расчёт с отсечением,
$O$ — без отсечения. Время берётся из фактических дочерних расчётов с теми же
n, φ, ядром и оптическими параметрами. Собранные матрицы и представления
префиксов не считаются дополнительными измерениями времени. Планировщик
консервативно учитывает отдельный $B_m$, даже если проверенное встроенное
сохранение префикса позволит его избежать. Кэш физических результатов
и кэш замеров времени остаются раздельными.

Если стоимости какого-либо уровня нет, локальное уточнение продвигает одну
группу связанных углов с наибольшей ошибкой. Все узлы её интерполяционного
шаблона и восемь seed сохраняются вместе. Неизвестное время записывается как
`null`, а не ноль; это ограничение ширины следующего шага, не обещание его
длительности. `round_work_limit.json` содержит наличие профилей, причину
ограничения и выбранный объём. `phi_production_work.json` описывает первый
проход после изменения φ. При восстановлении учитываются полные префиксы
всех восьми seed, в том числе готовые блоки, ещё не собранные в общий префикс;
неполные хвосты остаются в кэше для следующего шага. Критерии точности не меняются.

Если выходная матрица использует более длинные готовые префиксы, чем проверка
интерполяции этого раунда, исходные бюджеты и источники проверки сохраняются в
`interpolation_geometry_budget.csv` и `interpolation_geometry_sources.tsv`.
Независимый аудит восстанавливает остаток по ним, а статистику выходной матрицы —
по итоговым префиксам. Эти файлы также входят в контрольные суммы результата.

Важная проверка на реальных данных: для столбика 794,3×196,2 мкм, λ=0,532,
m=1,3116, участка 170,042–170,072°, восьми seed и N=512 на уровень остаточная
оценка составила 322,691% при смешанных φ=4/64 и 0,0329171% при общем φ=64.
Это снижение шума **проверочного остатка на этом участке**, не ошибка всей матрицы
и не измеренное ускорение всего расчёта. Уровни 14/16/18 считались без отсечения.

В полном DAT проверочный угол также может содержать интерполяцию, хотя для него
есть отдельный прямой расчёт. Для различения используйте `value_source` и
`point_type` в аннотированном CSV и `mueller_evaluated.dat`. Не заменяйте одни
значения другими постфактум без новой проверки принятого выходного оценивателя.

## Логи, результат и восстановление

### Рабочее состояние и периодический чекпоинт

Рабочее состояние — данные, которыми контроллер пользуется во время расчёта:
матрицы по каждому независимому seed, числа и начала выборок ориентаций,
параметры θ, φ и глубины, парные поправки и связи между блоками. Чекпоинт —
согласованная сохранённая копия этого состояния для восстановления после
завершения процесса. Это разные задачи хранения.

У нового расчёта по умолчанию `--fullauto-storage memory`. Результаты работника
передаются контроллеру по каналу между процессами порциями до 64 КиБ. Для
файловых интерфейсов ядра малое задание использует временный каталог в памяти:
суммарная оценка входа и выхода должна быть не больше 64 МиБ, с запасом
свободной памяти. Более крупное задание или недостаточный запас переключают
этот каталог на диск внутри выходной папки. Это временная запись без
принудительной синхронизации каждого файла, а не отдельный чекпоинт блока.
После передачи результата каталог удаляется; после аварийного завершения
остатки удаляются при следующем запуске только для уже не существующих PID.
Рабочее хранилище контроллера держит
содержимое в RAM, а при достижении своего лимита использует временное блочное
хранилище. Если сами имена и описания блоков перестают помещаться в лимит,
они переходят во временный каталог SQLite — базу данных для поиска записей.
Данные и каталог используют отдельные анонимные временные файлы в файловой
системе выходного каталога. Они освобождаются при завершении процесса, включая
SIGKILL, и не являются восстановимыми чекпоинтами. Их размер зависит от объёма
рабочего состояния: лимит RAM не является лимитом занятого места на диске.

Выборка, восемь независимых seed, корреляция парных поправок и критерии точности
не зависят от выбранного режима хранения. Сохранять только среднюю матрицу
недостаточно: для продолжения нужны раздельные наборы, бюджеты и состояние
адаптации. Поэтому копирование одного DAT не восстанавливает расчёт.

| Флаг | Действие |
|---|---|
| `--fullauto-storage memory` | Рабочие блоки в ограниченном кэше RAM; временные файлы содержат то, что не помещается. Стандарт для нового каталога. |
| `--checkpoint` | В fullauto включает снимки для восстановления с интервалом 300 секунд. В обычных поддержанных ориентационных режимах сохраняет прежний смысл. |
| `--fullauto-checkpoint-seconds 600` | Явный интервал сохранения 600 секунд; имеет приоритет над `--checkpoint`. |
| `--fullauto-checkpoint-seconds 0` | Отключает периодические снимки, в том числе при одновременном `--checkpoint`. Это стандарт без флагов сохранения. |
| `--fullauto-memory-mib 512` | Лимит рабочего хранилища контроллера, стандарт 512 МиБ. Это не общий лимит RAM процесса и не лимит видеопамяти. |
| `--fullauto-storage legacy` | Прежнее постоянное хранение отдельных вычислительных блоков и их зависимостей. Нужно для совместимости старых расчётов и диагностики. |

Лимит `--fullauto-memory-mib` включает удерживаемые байты блоков, их описания
и кэш каталога. В него не входят остальные индексы контроллера, память
вычислительных работников, временные строки и списки при чтении, код библиотек
и файловый кэш операционной системы. Кэш страниц SQLite ограничен меньшим
из значений: одна восьмая этого лимита или 1 МиБ; дополнительно учитываются
256 КиБ служебных расходов каталога. Это ограничение конкретного хранилища,
поэтому полный RSS процесса может быть больше.

SQLite загружается только при переносе каталога из RAM. На сервере должна
быть доступна библиотека `libsqlite3.so.0` либо `libsqlite3.so`. Небольшой
расчёт может работать без неё; если перенос потребуется, отсутствие библиотеки
даст явную ошибку. Заголовки SQLite при сборке не нужны; штатные Makefile
добавляют `-ldl` для динамической загрузки.

Интервал задаёт частоту запросов на сохранение. Снимок публикуется в безопасной
точке, где состояние согласовано; длинный вычислительный этап может задержать
запись. После сбоя восстанавливается последний успешно опубликованный снимок,
а не обещанный момент по таймеру. Программа сохраняет снимок с контрольной
суммой и атомарной публикацией: недописанная копия не заменяет прежнюю готовую.
Текущий снимок содержит все живые рабочие записи, включая сохранённые блоки
и их зависимости. Это ещё не минимальный набор сумм для восстановления;
время и размер сохранения растут с объёмом состояния. Фактические размеры RAM,
временных файлов и число снимков указаны в `fullauto_storage.json`.

| Файл нового режима | Назначение |
|---|---|
| `fullauto_storage.json` | Выбранный способ хранения, лимит и политика сохранения. |
| `memory_storage_v1.txt` | Маркер нового формата; не является восстановимым состоянием. |
| `fullauto_checkpoint.bin` | Последний полный опубликованный снимок для восстановления, если сохранение включено и снимок уже создан. |
| `fullauto_status.json` | Текущий статус и параметры; сам по себе не заменяет чекпоинт. |
| `public_snapshots/<hash>/` | Неизменяемое поколение опубликованной матрицы, её точности и параметров. Сохраняются текущая и предыдущая публикации. |
| `intermediate_current.json` | Атомарно обновляемая ссылка на полностью записанное публичное поколение; используйте её для чтения согласованных файлов. |

Явные `--fullauto-memory-mib` и `--fullauto-checkpoint-seconds` относятся к
`memory` и несовместимы с явным `--fullauto-storage legacy`. У старого режима
собственная политика сохранения каждого блока.

Пример длительного расчёта с восстановлением:

```bash
cpu/bin/mbs_po_mpi --method po --backend cpu \
  --particle 1 5 2 --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --checkpoint --output results/column_5um_recoverable
```

Чтобы продолжить, повторите ту же команду тем же бинарником в тот же каталог.
Файл частицы и его файл видимости, если он использовался, должны оставаться
доступны по исходным путям: они читаются до восстановления рабочего снимка.
Даже вход, расположенный внутри выходного каталога, нельзя удалять после
создания снимка. Чекпоинт не является переносимым архивом всех входных данных.
Явный интервал можно задать без краткого флага:

```bash
cpu/bin/mbs_po_mpi --method po --backend cpu \
  --particle 1 5 2 --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --fullauto-checkpoint-seconds 600 \
  --fullauto-memory-mib 512 --output results/column_5um_recoverable
```

Без чекпоинта после аварии сохранённые опубликованные матрицы остаются,
но незавершённую адаптацию необходимо начать заново в новом каталоге.
Служба, автоматически запускающая процесс после перезагрузки, сама по себе
не делает расчёт восстановимым: для нового режима ей тоже нужен `--checkpoint`.

Существующий каталог с прежними чекпоинтами автоматически выбирает `legacy`.
Изменение стандарта для новых запусков не отключает восстановление старой
серии и не удаляет её блоки. Не переносите старый расчёт в режим `memory`
простым добавлением флага; используйте новый каталог или отдельно проверенную
процедуру переноса.

### Прежнее хранение и восстановление (`legacy`)

Далее описаны файлы прежнего режима. Наличие опубликованного DAT или статуса
в режиме `memory` не означает наличие перечисленных ниже постоянных блоков.

При первом восстановлении старой папки актуальный контроллер создаёт общий
индекс `completed_jobs.journal`. Первый переход требует прочитать старые
метаданные; при следующих восстановлениях читается журнал и проверяются
только не вошедшие в него папки. Существующие матрицы и маркеры завершения
не переписываются. Индекс ускоряет поиск: хеши результатов и зависимости
источников всё равно проверяются до включения сохранённого блока в оценку.

При восстановимой ошибке бюджета RAM постоянный рабочий процесс освобождается,
а незавершённый блок повторяется один раз в новом процессе на тех же ориентациях.
Частичный результат не принимается; исходный журнал сохраняется как
`stdout.memory-retry.log`. Если сработал системный резерв RAM, контроллер ждёт
его восстановления не более 60 секунд после освобождения рабочего процесса.
Ожидание и повтор отражаются в `resource_wait.json` и журнале событий. Резерв
не уменьшается. Повторная нехватка памяти или другая вычислительная/CUDA-ошибка
останавливает задачу с сохранением завершённых чекпоинтов.

| Файл | Назначение |
|---|---|
| `fullauto_status.json` | Статус, параметры и последняя опубликованная оценка. Только `converged` означает прохождение включённых критериев. |
| `intermediate_current.json` | Ссылка на последний снимок матрицы; подходит для просмотра незавершённого расчёта. |
| `round_snapshots/` | Матрицы и точности предыдущих опубликованных раундов. |
| `parameters_accuracy.csv` | Производственные N по уровням, φ, оценки элементов и отношений в снимке. |
| `interpolation_orientation_budget.csv` | Отдельные N проверочного остатка в снимке. |
| `interpolation_output_policy.json` | Оператор интерполяции исходных 16 элементов; для некогерентной PO — `po-incoherent-piecewise-linear-v1`. |
| `mueller_fullauto.dat` | Принятая или опубликованная полная сетка; интерпретировать вместе со статусом. |
| `mueller_evaluated.dat` | Прямые вычисления текущего оценивателя. |
| `mueller_fullauto_annotated.csv` | Происхождение строк и оценки ошибок. Пустое поле не означает нулевую ошибку. |
| `execution_progress.json` | Текущие PID, GPU, пакеты, времена и число сохранённых заданий. Это не новая оценка точности. |
| `fullauto_history.jsonl` | История подбора и исполнения. |
| `controller_command.json` | Воспроизводимая команда. |
| `jobs/`, чекпоинты и индексы | Повторное использование завершённой работы. Сохраняйте каталог целиком. |

```bash
python3 -m json.tool results/column_5um/fullauto_status.json
python3 -m json.tool results/column_5um/intermediate_current.json
python3 -m json.tool results/column_5um/execution_progress.json
```

После отключения повторите исходную команду тем же бинарником и в ту же папку.
Завершённые блоки загружаются; незавершённый блок может повториться. Чекпоинт
версии 6 хранит производственный и остаточный бюджеты, а также φ остатка.
Поддержано чтение старых схем, но совместимость бинарников проверяется отдельно.
Нельзя вручную подменять хэш, редактировать готовые матрицы или переносить только
один TSV чекпоинта без зависимых блоков.

Политика интерполяции и версия проверки шума между углами входят в идентичность
планов проверки, снимков и решений об остановке. При смене политики незавершённый
расчёт сохраняет физические блоки и бюджеты, но заново проверяет точность;
старое прохождение не переносится на новый оператор. Итоговые контрольные суммы
включают `interpolation_output_policy.json`. Завершённый старый результат не
переписывается и не объявляется прошедшим новую проверку: для доуточнения создают
дочерний расчёт `--fullauto-refine-window`.

Проверка составных чекпоинтов переиспользует результаты обхода зависимостей
только внутри текущего раунда. Если среди запрошенных блоков есть родительский
блок и его зависимости, сначала проверяется родительский блок, затем сами
запрошенные зависимости. Все корневые блоки, их данные и контрольные суммы
прямых ссылок по-прежнему проверяются. План меняет порядок проверки, но не
порядок усреднения или состав выборки. План ограничен 512 корнями, 8 МиБ
описаний и 8192 связями; он не заменяет проверку целостности.

Если в `complete.txt` указан хеш списка источников, соответствующий список
обязателен. Его отсутствие считается повреждением чекпоинта, даже если итоговый
DAT сохранился. У составного блока это `angular_sources.tsv`; у обычного
парного расчёта глубин — `paired_depth.tsv`. Для парного оценивателя `balanced`
список угловых источников тоже обязателен. Файл может находиться внутри
проверенного архива: удаление его обычной копии после упаковки допустимо.
Старые нативные блоки без списка источников продолжают читаться.

При достижении лимита планирования уже прочитанные связи сохраняются.
Непрочитанные корни проверяются первыми: отсутствие прочитанного описания
не означает независимость блока. Если ограниченный план содержит больше
корней, чем проверяющих потоков, они обрабатываются группами до четырёх корней.
Следующая группа использует проверенные зависимости предыдущих групп. Это
устраняет повторные обходы, которые возникали при делении временного кеша
между всеми корнями сразу. Общий временный бюджет остаётся 64 МиБ: 32 МиБ
на результаты завершённых групп и 32 МиБ на работающую группу. В общий кеш
раунда эти результаты попадают только после успешной проверки всех корней.
Ошибка источника или исключение промежуточного обработчика не публикует
частичный результат проверки. Полные независимые планы сохраняют динамическое
распределение работы между потоками, без дополнительных групповых барьеров.

Параллельный сбор интегралов также использует уже проверенные в этом раунде
зависимости. Потоки читают общий кеш и добавляют результаты в собственные кеши;
общий временный лимит составляет 64 МиБ. Новые записи объединяются только после
успеха всей проверки. Кеш не служит подтверждением целостности после перезапуска
или в следующем раунде. Выбор исходных блоков, веса и арифметика интегралов
не меняются.

В `fullauto_history.jsonl` события `parallel_source_validation_plan` и
`parallel_source_validation` показывают порядок, число проверенных узлов,
число повторно использованных графов и время фаз. Событие
`parallel_source_validation_progress` появляется после завершения группы;
`validated_roots` и `completed_waves` показывают её продвижение. Это прогресс
проверки источников, поэтому `accuracy_recomputed` равен `false`: оптическая
точность не обновлялась. Один большой корень всё ещё может проверяться долго.
В `integral_summary.json`
поля `validation_checked_nodes`, `validation_reused_compound_graphs`,
`validation_temporary_memo_bytes` и `validation_temporary_memo_limit_bytes`
описывают проверку данных принятого оценивателя интегралов. Это диагностические
счётчики, а не дополнительные оценки оптической точности.

На трёх реальных вложенных графах Kika в опыте с ограниченным планированием
время проверки снизилось с 7,96 до 4,09 с, число проверок — со 137136 до 93752.
Хеши сохранённых матриц и происхождение данных совпали. Для набора из 63 корней
отдельно проверено сохранение всех корней в плане; весь большой граф повторно
для этого опыта не обходился. Ускорение 1,95× относится к указанному фрагменту
проверки, а не ко всему расчёту или гарантированной загрузке GPU.

Для сокращения числа файлов и синхронных записей доступен
[режим упакованных чекпоинтов](FULLAUTO_PACKED_CHECKPOINTS_RU.md).

Для нового бинарника `--fullauto-resume-compatible OLD_BINARY` допустим только
при подтверждённой совместимости конкретной пары бинарников и вычислительных
профилей. Сам факт успешной сборки такой совместимостью не является.
Для нового допуска или окна используйте документированный режим
`--fullauto-refine-window A B EPS` и сохранённую исходную конфигурацию; не
редактируйте физические параметры существующего каталога.

Служба Linux может автоматически возобновлять процесс после перезагрузки:

```bash
scripts/run_fullauto_service.sh mbs-column cpu/bin/mbs_po_mpi \
  results/column_service.log --method po --backend cpu \
  --particle 1 5 2 --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --checkpoint --output results/column_service
```

Этот скрипт устанавливает пользовательскую службу systemd и запускает её.
Он управляет процессом; численные решения остаются внутри программы.

## Память, загрузка GPU и границы метода

При выборе режима CUDA программа сначала прогревает вариант, затем выполняет
новый замер; время старого задания из кэша для выбора не используется.
Два лучших допустимых варианта проверяются повторно. Сравнивается полное время
запроса, включая подготовку и передачу результата. На одинаковых ориентациях
проверяются все 16 элементов и включённые нормированные отношения; явно
заданные параметры исполнения остаются фиксированными. Новые пробы ограничены
прогнозом стоимости основного расчёта и мягким бюджетом до пяти секунд.
Уже выполняющийся запрос не прерывается; если бюджета не хватает, сохраняется
исходный режим. Файл `kernel_calibration.json` содержит замеры, численные
проверки и причину выбора или отказа от переключения. Матрицы этих проб
временные и не становятся источниками данных для восстановления.

CPU трассирует и подготавливает пучки; CUDA вычисляет дифракцию и поддержанные
части трассировки. Постоянные рабочие процессы сохраняют CUDA-контекст и ограниченные
кэши. Готовые пакеты распределяются между GPU, проверка и сохранение данных
перекрываются с дальнейшей работой. Видеопамять занята пучками, угловыми буферами,
матрицами и рабочими областями; RAM — геометрией, подготовкой и кэшем блоков.

`--fullauto-trace-backend auto` сравнивает CPU, резидентную GPU-трассировку
(пучки остаются в видеопамяти) и совместную CPU+GPU-трассировку. Принимается
вариант, который быстрее минимум на 5% и проходит проверку всех 16 элементов
и отношений к M11 на одинаковых ориентациях. Порог расхождения —
`min(1e-7, EPS/1024)` для double и `min(1e-5, EPS/1024)` для float.
Результаты выбора сохраняются в `trace_backend_calibration.json`.
Для сравнения берутся 512–2048 ориентаций на seed, с ограничением
`--max-orientations`, в том числе при стартовой выборке 512.
Явный выбор `cpu`, `resident` или `hybrid` отключает поиск.

CPU-трассировка распределяет независимые ориентации между потоками; дерево
пучков одной ориентации обрабатывается последовательно. Число потоков подготовки
нужно согласовывать с физическими ядрами, доступными процессу через CPU affinity.
Например, при выделении восьми ядер новый расчёт запускают с `--threads 8`.
Для существующего CUDA-расчёта без явных флагов потоков используют совместимое
восстановление и `--fullauto-dispatch-threads 8`: меняются пулы подготовки и
аналитического среднего, исходные идентификаторы и настройка накопления сохраняются.
Этот флаг нельзя добавлять вместе с исходными `--threads`, `--po-prepare-threads`
или `--analytic-mean-threads`. Фактическое число показывает строка
`PO preparation threads` в журнале работника.

Выпуклый CPU-трассировщик переиспользует рабочий дочерний пучок и создаёт
выходной пучок после подтверждения пересечения с гранью. При нулевом поглощении
эффективный квадрат показателя преломления не зависит от угла падения;
повторные вычисления этого значения также исключены. Дополнительные флаги
не нужны. Геометрические проверки, порядок лучей, отсечения, выборка ориентаций
и способ накопления в чекпоинте сохраняются. Это уменьшает работу CPU при
подготовке данных для CUDA; выигрыш всей задачи зависит от доли этой работы.

Геометрия рёбер выпуклой частицы подготавливается один раз на ориентацию.
При пересечении с гранью каждая вершина проверяется один раз на ребро;
полностью сохранённый многоугольник не копируется заново. Допуски и формулы
пересечения сохраняются. Данные рёбер обновляются при каждом повороте,
в том числе при смене размера частицы.

Контроллер запоминает хеш параметров исполнения до изменения любого из них;
формат идентификаторов сохранённых заданий остаётся прежним. При планировании
углы и параметры запроса сравниваются как числа, без повторного преобразования
в текст. Уже готовое начало выборки исключается из оценки будущей работы только
после проверки наличия всех нужных углов у всех восьми seeds. Это ускоряет
прогноз стоимости, но не меняет сборку матрицы или критерий сходимости.
Индексы покрытия используют общий лимит 8 МиБ для всех вариантов φ;
при его заполнении выполняется прежний точный поиск. Дополнительные флаги
и новый формат чекпоинта не нужны. Эти изменения сокращают часть работы CPU,
но не гарантируют постоянные 100% загрузки GPU и не отменяют время сохранения
и проверки результатов.

Резидентный путь поддерживает выпуклые непоглощающие частицы до 32 граней,
24 вершин пучка и 18 внутренних столкновений, включая 20-гранный дроксталл.
Геометрия и оптическая фаза при подготовке остаются в double даже в сборке
float. Для частиц с более чем 16 гранями один пакет ограничен 64 ориентациями;
полное число ориентаций не сокращается. Очередь пучков зависит от числа граней
и глубины, а выделение памяти проверяет свободную VRAM. При переполнении весь
пакет пересчитывается на CPU. Некогерентный режим поддержан: матрица Мюллера
вычисляется для каждого пучка до суммирования, без межпучковой интерференции.
Поглощение и другие
неподдержанные варианты сохраняют CPU-подготовку.

Постоянный работник также запоминает консервативную оценку RAM на ориентацию
для одной физической задачи. После 128 измеренных ориентаций он может начать
следующий запрос с уже проверенного размера пакета вместо повторного разгона
от 16. Старт ограничен 256, предыдущим измеренным размером, явным
`--orientation-chunk` и текущей доступной RAM с дополнительным запасом 2×.
Это не кэш матриц и не изменение выборки. Сообщение `Prepared memory reuse`
показывает оценку и стартовый пакет; кэш пучков можно независимо отключить
через `--trace-cache-mib 0`.

В очереди совместимые угловые пакеты одного seed, префикса, n и φ идут подряд,
чтобы подготовленные пучки реже вытеснялись из ограниченного кэша другими seeds.
Выигрыш возможен, когда пучки одного задания помещаются в кэш; объём памяти
и число рассчитываемых ориентаций не увеличиваются. Короткий пакет может
оставаться после вычитания уже сохранённых углов или разделения по n и φ.

`execution_progress.json` содержит счётчики сохранённых блоков текущей фазы
и последние 16 завершённых блоков с seed, offset, N, n, φ и границами θ.
Между границами могут быть пропуски; точные углы находятся в файлах задания.
Это выполненная работа, а не новая оценка ошибки и не процент готовности всего
адаптивного раунда. Оценка точности берётся из `intermediate_current.json`.

Загрузка GPU может падать при трассировке, сборке префиксов, проверке и I/O.
100% загрузки не является критерием ни правильности, ни минимального времени.
Большой пакет снижает накладные расходы, но повышает память и задержку публикации.
Контроллер ограничивает память и объём работы; OOM или исчерпание диска не являются
успешным завершением. Текущее время задания видно отдельно от возраста оценки.

## GO и extinction-only

```bash
cpu/bin/mbs_po_mpi --method go --backend cpu \
  --particle 1 100 50 --ri 1.3116 0 --wavelength-um 0.532 \
  --fullauto 0.02 --output results/column_go
```

GO — геометрическая оптика: α усредняется аналитически; конечные угловые ячейки
считаются напрямую, PO-интерполяции нет. Полюсные дельта-вклады
сохраняются отдельно в `mueller_forward.dat` и `mueller_backward.dat`; это
интегральные массы, не значения гладкой диаграммы в градусной точке.

GO mirror по умолчанию выключен. Явное включение поддерживает непоглощающие
встроенные типы 1 и 10 с допустимыми симметриями; зеркальная пара восстанавливается
через (M+PMP)/2, P=diag(1,1,−1,−1), включая полюсные вклады. Это не простое
удвоение числа симметрий. Файловые формы и поглощение не принимаются как поддержанные.
Подробности: `GO_MIRROR.md` и `GO_BALANCED.md`.

`--extinction-only` — отдельный CPU-режим PO с Hammersley для выпуклой геометрии.
Он вычисляет экстинкцию по оптической теореме без угловой сетки матриц; не является
fullauto и не даёт полного интеграла рассеяния или точного альбедо. Примеры:
`EXTINCTION_ONLY.md`.

## Шум соседних опорных углов в некогерентном режиме

При локальном подборе N в некогерентной PO дополнительно проверяется шум
разностей соседних опорных матриц и трёхточечных изгибов на восьми независимых
наборах. Не прошедшие группы уточняются совместно. Политика v4 задаёт
`allowance_j = min(allowance_v3,j, ε/32)`: сохраняет более строгие пределы слабых
элементов и ограничивает шум сильных. При ε = 4% потолок равен 0,125% M11.
Ограничивается статистическая неопределённость контраста после вычитания его
среднего, а не физический наклон или изгиб. Точечный допуск ε не заменяет эту
проверку; сохранённые опорные матрицы не сглаживаются. Подробные формулы,
определения и диагностика: [согласование углов](FULLAUTO_ANGULAR_SAMPLING_RU.md).

Модульные проверки v4, линейной интерполяции и восстановления пройдены, включая
сохранённые реализации проблемных столбиков. Полное сравнение старого и нового
fullauto на малой частице CPU/CUDA пока выполняется; результатов о скорости
и развёртывании этого изменения на рабочих задачах здесь ещё нет.

## Объём рабочих файлов

Новые рабочие запуски fullauto автоматически используют `--no-text-reports`:
не создают дубликаты `*_log.txt` и `*_out.txt`. Основной `stdout.log`, матрицы,
интегралы, команды и файлы восстановления сохраняются. Это действует для PO/GO
и обоих способов запуска рабочих процессов. Подробности и тесты:
[хранение результатов](FULLAUTO_STORAGE_RU.md).

## Паузы между короткими пакетами

Постоянный рабочий процесс сохраняет часть освобождённой памяти для следующего
пакета. Раньше при RSS выше 256 МиБ он вызывал `malloc_trim` после каждого задания:
это возвращало страницы операционной системе, после чего подготовка пучков снова
выделяла и заполняла их. Теперь очистка выполняется при завершении задания, если
прошло 5 секунд либо 64 задания, или RSS вырос более чем на 256 МиБ относительно
последней очистки. Периодическая очистка нужна только при RSS выше 256 МиБ.

При приближении к резерву RAM (резерв плюс 256 МиБ), достижении 75% заданного
`MBS_HOST_MEM_BUDGET_MB` или невозможности прочитать счётчики памяти очистка
выполняется сразу на ближайшей границе заданий. Внутренние ограничения памяти
подготовки пучков продолжают действовать. Это ограниченная задержка возврата
освобождённых страниц, а не отмена защиты от нехватки RAM. В `stdout.log` записаны
`trim_reason`, `trim_seconds` и RSS до и после очистки. Дополнительный флаг не нужен.

Тест на GPU2 с реальными пакетами столбика 794,3 мкм, некогерентным PO и поправкой
balanced при текущих 12 потоках и 8 потоках подготовки дал 9,81 → 9,16 с на
прогретую серию: около 7% ускорения данного рабочего этапа. Максимальный RSS,
измеренный после ответов рабочего процесса, вырос с 642–663 до 749 МиБ. Это
измерения на границах заданий, а не максимальный расход внутри задания.
Отдельный непрерывный тест 128 заданий показал плато удерживаемой памяти.
Все 16 элементов и вложенные матрицы проверены; наибольшее различие,
нормированное на M11, и различие нормированных отношений не превышали
9,8·10⁻⁸. Этот результат не измеряет полное время адаптивного раунда: чтение
старых контрольных точек и сборка характеристик по-прежнему могут задерживать GPU.

## Эксперимент: один рабочий процесс с ограниченными GPU-буферами

Эта комбинация включается явно для отдельной проверки. Она не заменяет простой
запуск в начале руководства, не означает обновление рабочих очередей и не
гарантирует загрузку GPU от 50%. Нужен CUDA-бинарник с этими изменениями
(путь ниже — пример) и новый каталог результата:

```bash
env -u MBS_GPU_TRACE_CONVEX_WORKSPACE_MIB \
  MBS_GPU_TRACE_DEEP_CAPACITY=1 \
  MBS_GPU_TRACE_CAPACITY_HINT=1 \
  MBS_GPU_TRACE_BUFFER_POOL=1 \
  MBS_GPU_RESIDENT_REUSE=1 \
  MBS_GPU_RESIDENT_BOUNDED_REUSE=1 \
  MBS_GPU_RECYCLE_PREPARED=1 \
  MBS_HOST_MEM_BUDGET_MB=4096 MBS_GPU_MEM_FRACTION=.20 \
  gpu/bin/mbs_po_gpu_float_ds \
    --method po --backend cuda --incoherent \
    --particle 1 501.2 155.8 --wavelength-um 0.532 --ri 1.3116 0 \
    --symmetry 2 6 --fullauto 0.04 --fullauto-theta-range 150 160 \
    --fullauto-gpus 0 --fullauto-workers persistent --threads 8 \
    --po-trace-backend resident --allow-experimental-environment \
    --output results/column501_resident_experiment --close
```

Это один расчёт fullauto: один контроллер и один постоянный вычислительный
процесс на GPU 0, без нескольких независимых задач. `0.04` означает допуск 4%;
финальные проверки остаются включёнными. Размеры столбика L=501,2 и D=155,8 мкм.
Для когерентной PO уберите `--incoherent`. Явный resident-backend всё равно
проверяет поддержку режима. В команде выше resident-контроль граней намеренно
не включён: этапы с обычным контролем граней сохраняют CPU-подготовку.

| Настройка | Что делает |
|---|---|
| `MBS_GPU_TRACE_DEEP_CAPACITY=1` | Разрешает опорную GPU-трассировку до глубины 22 с ограниченными очередями и максимум двумя попытками увеличения ёмкости. Не фиксирует выбранное число отражений. |
| `MBS_GPU_TRACE_CAPACITY_HINT=1` | Запоминает достаточную ёмкость очередей для того же рецепта; требует deep capacity. Оптические результаты не подменяет. |
| `MBS_GPU_TRACE_BUFFER_POOL=1` | Повторно использует память трассировки, включая рабочие очереди. Сохраняет не больше 2 ГиБ и четверти суммы свободной VRAM и собственных удерживаемых буферов. |
| `MBS_GPU_RESIDENT_REUSE=1` и `MBS_GPU_RESIDENT_BOUNDED_REUSE=1` | Повторно используют буферы подготовки/дифракции с отдельным пределом не выше 1 ГиБ и динамическими ограничениями памяти. Явный `MBS_GPU_RESIDENT_REUSE=0` сильнее. |
| Дополнительный `MBS_GPU_RESIDENT_FACET_CONTROL=1` | Только для отдельного опыта на крупных частицах/большой глубине: разрешает обычный аналитический контроль граней вместе с resident-трассировкой. Контроль остаётся на постоянном потоке обработки; GPU-этапы идут последовательно, включая переход после CPU fallback. |
| `MBS_GPU_RECYCLE_PREPARED=1` | Возвращает завершённый CPU-пакет потоку подготовки для освобождения памяти; ограничение двух пакетов сохраняется. |

Бюджет RAM 4096 МиБ и доля GPU `.20` — настройки теста, а не универсальный подбор
или жёсткие пределы полного RSS/VRAM. Пулы ограничивают собственные выделения;
CUDA-контекст, матрицы, аналитические рабочие массивы и другие данные также
занимают память.

Для отдельного сравнения на крупной частице или большой глубине добавьте
`MBS_GPU_RESIDENT_FACET_CONTROL=1` к назначениям `env` выше. Не включайте его
для всей очереди: в fullauto-тесте с выбранной малой глубиной n=6 расчёт стал
**медленнее** — 19,582 → 28,085 с некогерентно и 24,719 → 27,144 с когерентно.
В каждой паре выполнены одинаковые 160 native-заданий и 236 448 ориентаций.
Ограничение resident-пакета увеличило число пакетов с 569 до 2400. Численное
сравнение пройдено: наибольшее отличие по всем элементам `4,125·10⁻⁷ M11`.
Этот результат исключает рекомендацию флага как общего ускорения: backend
нужно выбирать по измерению представительной задачи.

Формула контроля не меняется: выборочные вклады отражения и тени получают те же
веса ориентаций; в M11 добавляется известное среднее минус выборочная оценка
с прежними коэффициентами для каждого θ. Матрицы парной глубины и префикса
сохраняют свою нормировку. Аналитический контроль назад, диагностические
выборки по отдельным ориентациям, Gaussian azimuth, hybrid-трассировка,
поглощение и невыпуклая/неподдержанная геометрия не получают этот новый путь:
для них остаются прежняя CPU-подготовка и проверки совместимости. Проверяйте
`accepted_GPU`, `CPU_fallback` и `GPU resident facet control` в журнале.

При включённом trace-пуле **неявный GPU raw-cache пучков равен нулю**.
CPU-кэш `PreparedReuse` постоянного рабочего процесса сохраняет прежний предел
256 МиБ с уменьшением по RAM. Строка `Trace caches` показывает оба действующих
предела. Явный `--trace-cache-mib N`, включая ноль, по-прежнему задаёт **оба**
кэша после прежних RAM-ограничений. `MBS_GPU_TRACE_CONVEX_WORKSPACE_MIB=0`
отключает сохранение trace-буферов, но не включает raw-cache обратно, пока
выбран `MBS_GPU_TRACE_BUFFER_POOL=1`. При выключенном флаге пула неявная политика кэшей
остаётся прежней.

Новый запуск по-прежнему использует рабочее хранилище memory. Для восстановления
добавьте `--checkpoint`: снимок сохраняется каждые 300 секунд. Явный
`--fullauto-checkpoint-seconds N` сильнее, включая ноль. Без снимка опубликованная
матрица не позволяет продолжить прерванную адаптацию. Восстановление требует
той же команды, бинарника, output и доступных исходных файлов частицы; работа
после последнего снимка может повториться.

Проверены четыре парных native GPU-теста, когерентно и некогерентно:
512 ориентаций, пять углов θ, 32 точки φ, глубина 22, парная глубина 20 и префикс
256 ориентаций. Все 16 элементов, нормированные отношения, контроли и интегралы
прошли сравнение с CPU-трассировкой и GPU-дифракцией. Наибольшее отличие матриц —
`8,88·10⁻⁷ M11`, выборочных контролей — около `1,5·10⁻¹⁷ M11`.
Это проверка численного совпадения данного примера, а не оценка времени полного
fullauto или ускорения на других формах. Загрузка общей карты в `nvidia-smi`
не равна доле времени ядер именно этого рабочего процесса.


## Завершение fullauto по умолчанию

Для PO и GO достаточно одного успешного рабочего прохода. Финальные
пересчёты по умолчанию выключены: `--fullauto-final-checks off` больше не
требуется писать. Для расширенного аудита укажите `--fullauto-final-checks on`.
Он не включает второй успешный рабочий проход автоматически. Повторы задаются
явно через `--convergence-passes N` или `controller.stable_passes` в конфигурации.
Конфигурация, которая не задаёт этот ключ, не меняет один проход по умолчанию.

Явные `--fullauto-final-audit on` и `--fullauto-physics-audit on` также
включают финальные проверки, если общий переключатель не задан. Явное
`--fullauto-final-checks off` имеет приоритет над отдельными аудитами.
Стартовый подбор глубины, восемь независимых наборов, рабочие проверки
элементов, отношений и устойчивости сохраняются. В PO сохраняется проверка
интерполяции. Пропущенные финальные проверки помечаются как невыполненные;
их отсутствие не является подтверждением физической точности.

Новый режим применяется при запуске нового бинарника. Уже работающие процессы
не меняются. Завершённые результаты с другой политикой проверок не переписываются.


### Ускорение подготовки при поглощении

Восстановление внутренних оптических путей трёх опорных точек и центроида
(при стандартной одной пробе поглощения) выполняется
пакетом без изменения числа отражений и допуска. На проверенном полном
fullauto добавление центроида к пакету сократило время ещё на 4,3%
относительно варианта с тремя общими путями; это не универсальный коэффициент.
[Измерения, ограничения и скалярный режим сравнения](INTERNAL_OPTICAL_PATHS_20261116_RU.md).

## Несколько внутренних работников на одной GPU

`--fullauto-gpu-workers 1|2|4` задаёт число независимых внутренних работников
на каждой выбранной GPU. По умолчанию используется один. Это одна команда
`fullauto` и один контроллер точности: работники получают независимые задания
по ориентациям, а контроллер собирает их в прежнем порядке. Формулы, выборка
и критерий завершения от этого флага не меняются.

Режим предназначен для CUDA PO. Он может сократить ожидание GPU между пакетами
трассировки. Если GPU уже занята другими расчётами, дополнительные работники
могут только усилить конкуренцию; флаг не включается автоматически.

Пример для одной выделенной карты и 12 физических CPU-ядер:

```bash
MBS_HOST_MEM_BUDGET_MB=1024 MBS_GPU_MEM_FRACTION=0.125 \
  taskset -c 0-11 ./mbs_po_gpu_float_ds \
  --method po --backend cuda --particle 4 32.35 71.81 5 \
  --wavelength-um 1.550 --ri 1.2906 0.00042407 --symmetry 2 6 \
  --fullauto 0.04 --fullauto-theta-range 0 180 --fullauto-gpus 0 \
  --fullauto-gpu-workers 4 --fullauto-dispatch-threads 3 \
  --fullauto-workers persistent --fullauto-resources off --fullauto-memory-mib 1024 \
  --output droxtal_10um_1550nm --close
```

Проверьте соответствие номеров CPU физическим ядрам своей машины: номера
`0-11` приведены для конкретного размещения, а не как универсальная маска.
При `--fullauto-gpu-workers` программа отклоняет размещение, если число работников, умноженное на число
их потоков, превышает доступное через CPU affinity число физических ядер.
Всего разрешено не больше восьми работников и не больше четырёх на GPU.

`--fullauto-dispatch-threads` обязателен при двух/четырёх работниках. Он задаёт
пулы подготовки и аналитического среднего одного работника. Не сочетайте
его с отдельными `--threads`, `--po-prepare-threads` и
`--analytic-mean-threads` в новом расчёте.

Автоматические лимиты RAM и VRAM делятся между работниками. Явные переменные
`MBS_HOST_MEM_BUDGET_MB` и `MBS_GPU_MEM_FRACTION` задают лимит **одного**
работника. В примере это суммарно 4096 MiB бюджетов работников и доля GPU
0.50; память контроллера и служебные расходы идут дополнительно. Доля GPU
одного работника не может превышать `0.88 / число_работников_на_GPU`.
Эти оценки не являются жёсткими ограничениями памяти ОС.

Выбирайте фиксированный список `--fullauto-gpus`, а не `auto`. При обычном
восстановлении используйте те же параметры запуска и тот же каталог.
Для смены размещения существующего расчёта применяйте отдельно совместимое
восстановление и `--fullauto-dispatch-gpus 0,0,0,0`; одновременно задавать
`--fullauto-gpu-workers` (включая значение 1) и
`--fullauto-resume-compatible` нельзя.

Фактическое число слотов записывается в `active_worker_slots`, а число
работников на GPU и их лимиты — в события `worker_start`.

Измерение 17.11.2026 на RTX 3080 Ti (gpu2): дроксталл Dmax=10 мкм,
λ=1,55 мкм, m=1,2906+0,00042407i, когерентный PO, θ=0–180°, допуск 4%.
Последовательность ABA: один исполнитель × 12 CPU-потоков — 252,08 с;
четыре × 3 потока — 183,11 с; повтор одного × 12 — 250,13 с.
Это 1,37× по времени полного расчёта (сокращение на 27,1%).
Средняя загрузка GPU — 45% против 75%; полной загрузки на протяжении всего
запуска этот режим не гарантирует. Пиковый суммарный RSS исполнителей вырос
с 2312 до 2818 МиБ (контроллер в эти числа не включён).
Все варианты завершились на раунде 5 с оценкой 3,23%, n=10, φ=4,
158 непосредственно вычисленными углами. Максимальное различие всех 16
элементов относительно M11 — 2,25e-7; нормированных отношений — 2,49e-7.
Это измерение отдельной задачи на освобождённой карте, а не доказательство
такого же выигрыша при одновременных трёх производственных задачах на GPU.
Подробные команды, матрицы и графики находятся в артефакте
`native_four_workers_20261117/report.html` рабочего каталога экспериментов.

Повтор на окончательном бинарнике (SHA256 начинается с `f749b59f75f8`):
252,19 / 181,11 / 251,17 с — 1,39×, на 28,0% меньше времени. Те же параметры
сходимости и сетки; максимальное различие всех 16 элементов — 2,064e-7 M11,
отношений к M11 — 2,427e-7. Средняя загрузка GPU 39–40% против 72,8%,
пиковый RSS четырёх работников 2819,5 МиБ. Таким образом, полный выигрыш
на этой задаче воспроизведён в двух сериях ABA (1,37× и 1,39×).
Восемь проверок неверных ресурсов/совместимости прошли до запуска работников.
Матрицы, команды и отчёт повторной проверки:
`four_workers_stability_20261117/report.html` рабочего каталога экспериментов.

Продолжение проверки на той же задаче (17.11.2026): фиксировать `--chunk 64`
невыгодно — ABA 189,12 / 191,13 / 183,11 с против автоматического пакета.
Средняя загрузка GPU при этом выросла примерно с 75% до 79%, то есть сама
загрузка не заменяет измерение времени до готового результата. Изменился
выбор интерполяционных опор: 157 прямых углов вместо 158; общие 155 прямых
значений отличаются менее чем на 8,34e-8 M11, полный DAT — до 6,25e-4 M11.

Изолированный NVIDIA MPS также не дал ускорения: 183,11 / 183,14 / 182,11 с
(без MPS / с MPS / без MPS), с теми же 12 CPU-ядрами, включая сервер MPS.
Первый контроль взят из непосредственно предшествующего теста пакетов.
Сетка и численная точность сохранены. Поэтому MPS не является обязательным
сервисом режима и не включён автоматически. Полные материалы:
`fullauto_followup_20261117/report.html` в каталоге экспериментов.

### Как измерять CPU-трассировку после подготовки конвейера

В `tests/test_convex_trace_fingerprint.cpp` добавлен режим `bench-reuse`:
один объект частицы, трассировщик и ёмкость выходного массива используются
для последовательности ориентаций, как внутри рабочего пакета подготовки.
Режим `bench` сохраняет измерение с новыми объектами на каждой ориентации.
Без аргументов тест теперь сравнивает свежий и переиспользуемый трассировщики:
432 случая для столбика, буллита и дроксталла, три масштаба, с поглощением и
без него, включая граничные ориентации. Сравниваются точные вершины, матрицы
Джонса, оптические пути, номера траекторий и порядок 3,99 млн пучков.
Тест следует собирать с включёнными `assert`: при `NDEBUG` сборка явно
отклоняется, поскольку иначе вызовы трассировки внутри проверок исчезли бы
и измерение показывало бы ложное ускорение.

Не трактуйте время `bench` как скорость рабочего fullauto. На этой системе
один и тот же объём трассировки занимал около 48 с с новым выходным массивом
для каждой ориентации и около 18–19 с с повторным использованием буфера.
Это различие тестовых условий, а не новое ускорение программы: рабочий цикл
уже переиспользовал буфер. Выборочный профиль оптимизированного бинарника
с переиспользованием отвёл около 25% CPU-времени проверке стороны ребра,
9% — остальной части пересечения, 7,5% — проекции на грань. Это отдельный
CPU-тест n=18, не доли времени GPU или полного адаптивного расчёта.

Проверенные далее пул пучков, формирование выхода непосредственно в массиве,
SIMD-классификация вершин и предварительная оценка стороны ребра не дали
устойчивого выигрыша; в рабочий вычислительный код они не включены.

Дополнительная проверка настроек компилятора на том же тесте с буферами:
отключение разворачивания циклов не помогло (отношения времени базовой
сборки к кандидату 1,003 / 0,983 / 0,994). `-fno-math-errno` дало лишь
1,008 / 1,023 / 1,022 на фоне дрейфа контрольных измерений; это не основание
обещать существенное ускорение полного расчёта. Профильная оптимизация
компилятора, обученная на граничных ориентациях, дала 0,995 / 1,007 на другой
выборке, а контрольная сумма чисел изменилась. Эти варианты не включены
в рабочую сборку. Данные: `compiler_steady_20261117` и
`pgo_trace_20261117` в каталоге экспериментов.

### Плотная угловая сетка и трассировка выпуклой частицы

Для когерентной физической оптики можно включить два ускорения в том же запуске:

```bash
MBS_ANALYTIC_BINNED_EDGES=1 MBS_CONVEX_FACET_BOUNDS=1 \
  ./gpu/bin/mbs_po_gpu_float_ds --method po --backend cuda \
  --particle-file particle.dat --resize-dmax-um 10 \
  --wavelength-um 0.355 --ri 1.3243 0 --symmetry 1 1 \
  --fullauto 0.04 --fullauto-theta-range 0 180 \
  --allow-experimental-environment --output result
```

* `MBS_ANALYTIC_BINNED_EDGES=1` ускоряет подготовку средних отражения. Узлы исходной квадратуры Гаусса группируются по расстоянию между точками на рёбрах. Внутри одного интервала кубической интерполяции достаточно четырёх взвешенных моментов. Для группы, пересекающей границу интервалов, программа оценивает ошибку. Если оценка для угла превышает `1e-8` от модуля суммы, она выполняет исходную квадратуру. Группировка применяется при 96 и более ожидающих углах, когда на один радиальный интервал приходится достаточно узлов. Независимые проверки точности матрицы в `fullauto` продолжают работать.
* Ключ кэша этого режима учитывает сетку углов. Для частого чередования двух сеток или режимов укажите отдельный путь `--analytic-mean-cache` для каждого. У обычного режима сохраняется совместимость с прежним кэшем строк.
* `MBS_CONVEX_FACET_BOUNDS=1` строит ограничивающий прямоугольник пучка в поперечной плоскости. Если проекция грани заведомо вне прямоугольника, CPU пропускает её до пересечения многоугольников. Для близких границ, скользящего падения и острых граней сохраняется детальная проверка. Опция действует в выпуклом CPU-трассировщике, в том числе когда дифракция считается на CUDA.

В проверочном CPU-пакете из 64 ориентаций на 2454 углах для произвольной частицы 10 мкм при λ = 0,355 мкм исходный код, код с обеими опциями и повтор исходного заняли 27,92, 8,58 и 26,52 с. Подготовка аналитических средних заняла 19,08, 1,04 и 19,02 с. Максимальное расхождение по 16 элементам составило 1,59·10⁻¹³ от M11. Эти времена относятся к одному пакету при фиксированных n = 10 и φ = 8.

На RTX 3080 Ti для той же частицы измерили также время полного когерентного `fullauto` с допуском 4% на 0–180°. В этом опыте сборка из ветки `perf/fullauto-row-cost-benchmark` дополнительно подбирала азимутальную сетку с учётом стоимости трассировки и дифракции. Исходная сборка заняла 583,26 с, ускоренная — 267,59 с, повтор исходной — 606,95 с. Ускорение относительно более быстрого контрольного запуска составило **2,18×**. Все три запуска выбрали глубину 10 и 16 азимутов. При сравнении всех 16 элементов на 2454 углах максимальное расхождение составило 0,904% от контрольного M11 на соответствующем угле. Для нормированных элементов максимум составил 0,518 процентного пункта. [Параметры запуска, контрольные суммы и результаты обоих сравнений](https://github.com/KirillSalnikov/MBS-fast/blob/114513dad01cc7e7b43e1164e20f3dabdeb7c3e9/benchmarks/fullauto_row_cost/dense_mean.json).

### Общий кэш аналитических средних при смене углов θ

При включённом `MBS_ANALYTIC_BINNED_EDGES=1` можно добавить `MBS_ANALYTIC_LAZY_REFERENCE=1` в ту же команду. Когда `fullauto` передаёт общую опорную сетку из 96 и более углов и путь к кэшу, программа определяет по этой сетке границы радиальных интервалов. При каждом запросе она вычисляет и добавляет в файл только недостающие углы. Поэтому пилот, рабочая сетка и повторная проверка используют одни и те же аналитические средние на общих углах. Смена геометрии, оптики или опорной сетки обновляет содержимое кэша.

На произвольной частице воспроизвели пять запросов с тремя сетками из завершённых расчётов. В таблице приведено отношение более быстрого из двух контрольных времён к времени нового режима. В обоих вариантах группировка узлов на рёбрах уже была включена.

| 10 | 0,355 | 65 / 191 / 377 | 5,26× | 1,46× |
| 31,62 | 1,550 | 65 / 142 / 282 | 3,21× | 1,10× |

Каждый запрос физической оптики использовал 16 ориентаций и 16 азимутов. Максимальное отличие по всем 16 элементам составило 2,34·10⁻¹³ от M11 соответствующего угла. Для данной таблицы время полного адаптивного расчёта на GPU измеряется отдельно.

### Прямой расчёт угла при дорогом уточнении интерполяции

Для когерентной физической оптики с локальным подбором ориентаций можно задать `MBS_FULLAUTO_INTERPOLATION_KNOT_COST=1` перед обычной командой запуска. Если проверочный угол превышает допуск интерполяции, контроллер оценивает два варианта работы. Он может увеличить число ориентаций на прежних углах или включить проверочный угол в опорную сетку и проверить соседние интервалы. Оценка применяется при одном уровне выборки для остатка интерполяции, общем числе азимутов и одинаковом числе уже рассчитанных ориентаций в узлах интерполяции. Решение о добавлении узла отмечается в журнале как `interpolation_knot_cost`, а в таблице уточнения как `refine_theta_cost`. Новый интервал проходит обычную проверку матрицы и нормированных элементов. По умолчанию действует прежний порядок уточнения.

На дроксталле 31,62 мкм при λ = 1,55 мкм контроллер добавил в опорную сетку угол 69,123° после первой неудачной проверки M44. На восьми независимых выборках по 40 углам максимальная верхняя граница ошибки интерполяции снизилась с 1,075% до 0,667% при допуске 1%. В отдельном CPU-замере без отсечения пучков воспроизвели работу после первой неудачной проверки для двух выборок. Контроль занял 397,84 и 398,70 с, уточнение сетки с прямым расчётом новых углов заняло 186,01 с. Ускорение **2,14×** относится к этому участку расчёта.
